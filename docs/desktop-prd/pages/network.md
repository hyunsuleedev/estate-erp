# Network

## 메타

- 페이지명: Network
- 문서 상태: draft
- 우선순위: P0
- Phase: Phase 2
- 구현 상태: placeholder only
- 작성일: 2026-04-02
- 최종 수정일: 2026-04-02
- 관련 엔터티: NetworkRoom, NetworkRoomMember, NetworkSharedProperty, NetworkInquiry, NetworkMessage, Listing, Property, Office, User, Notification, Task, Deal(future)
- 관련 API:
  - `GET /network/rooms`
  - `POST /network/rooms`
  - `GET /network/rooms/:id`
  - `POST /network/rooms/:id/join`
  - `PATCH /network/rooms/:id/members/:officeId`
  - `GET /network/rooms/:id/shared-properties`
  - `POST /network/shared-properties`
  - `PATCH /network/shared-properties/:id`
  - `POST /network/shared-properties/:id/inquiries`
  - `PATCH /network/inquiries/:id`
  - `GET /network/rooms/:id/messages`
  - `POST /network/rooms/:id/messages`
- 관련 화면: Listings, Deals, Tasks, Notifications

현재 결정:

- 이 문서는 desktop의 `네트워크 메인 페이지`를 기준으로 작성한다.
- 이 페이지는 단순 게시판이 아니라 `공동 중개 방 + 공유 매물 + 문의/응답 + 채팅`을 함께 다루는 작업공간이다.
- route는 현재 `/network` 하나지만, 실제 UX는 `상단 보드 탐색 + 좌측 방 목록 + 중앙 매물/문의 + 우측 채팅/활동`의 다중 레이어가 적합하다.
- 메인 진입에서는 `전체 게시판`, `내 모임`, `지역 모임`, `공동중개` 같은 보드형 탐색 레이어가 먼저 있고, 그 안에서 룸 상세 작업공간으로 내려가는 구조가 좋다.
- `공동중개` 보드 안에는 최소 `공유매물`, `구합니다` 두 탭이 필요하다.
- `공유 매물`의 핵심은 `Listing을 네트워크에 다시 게시`하는 것이지, 별도 매물을 새로 만드는 것이 아니다.
- 공유 시에는 `동/호/층/메모/사진` 등 민감 정보를 필드 단위로 마스킹할 수 있어야 한다.
- 네트워크 문의는 단순 채팅이 아니라 `공유 매물에 대한 사무소 간 공식 접촉`으로 본다.
- 장기적으로는 네트워크 문의 수락 후 `Deal` 또는 `공동중개 건`으로 이어지는 흐름이 필요하다.

## 1. 페이지 목적

- 이 페이지가 해결해야 하는 핵심 업무:
  - 참여 중인 네트워크 룸을 빠르게 찾고 관리한다.
  - 게시판/모임/공동중개 보드 관점에서 필요한 네트워크 영역으로 빠르게 진입한다.
  - 내 Listing을 방 단위로 공유하고 공개 범위를 조절한다.
  - 다른 사무소가 올린 공유매물/구함 요청을 조건 검색으로 탐색한다.
  - 다른 사무소가 올린 공유 매물을 탐색하고 문의한다.
  - 문의/응답, 채팅, 최근 활동을 한 곳에서 본다.
- primary 사용자:
  - agent
- secondary 사용자:
  - manager, owner
- 이 페이지가 필요한 이유:
  - 공동중개는 실제로 `누가 어떤 매물을 어떤 조건으로 공유했고 누가 응답했는지`가 중요하다.
  - 외부 메신저로 흩어지면 감사 추적, 응답 누락, 정보 마스킹 관리가 어렵다.
  - 이 기능은 단순 CRM이 아닌 Estate ERP의 핵심 차별점이다.

## 2. 사용 시점

- 사용자가 이 페이지에 들어오는 대표 상황:
  - 내가 참여 중인 네트워크 룸의 새 공유 매물을 확인할 때
  - 전체 네트워크 보드에서 최근 공동중개 매물을 탐색할 때
  - 내 매물을 특정 룸에 공유할 때
  - 특정 지역/가격/면적 조건으로 공동중개 매물을 검색할 때
  - 다른 사무소가 공유한 매물에 문의를 보낼 때
  - 들어온 문의에 승인/거절 응답을 줄 때
  - 룸 참여 요청과 멤버 상태를 확인할 때
- 진입 경로:
  - 사이드바 `네트워크`
  - Listing Detail의 `네트워크 공유`
  - Notification의 `network_inquiry`, `network_join_request`
- 이전 화면:
  - Listings
  - Notifications
  - Tasks
- 다음 화면:
  - Room Detail Workspace
  - Listing Detail
  - Deal Detail(future)
  - Task Detail
- 이 페이지를 나가는 대표 액션:
  - 룸 선택
  - 매물 공유
  - 문의 전송
  - 문의 응답
  - 메시지 전송

## 3. 사용자 역할과 권한

| 역할 | 조회 | 생성 | 수정 | 삭제 | 승인/확정 | 비고 |
| --- | --- | --- | --- | --- | --- | --- |
| owner | 전체 조회 | 가능 | 가능 | 가능 | 가능 | 룸 생성/멤버 승인/공유 정책 결정 |
| manager | 전체 조회 | 가능 | 가능 | 제한적 | 가능 | 팀 대외 네트워크 운영 |
| agent | 승인된 룸 조회 | 가능 | 제한적 | 제한적 | 가능 | 실무 공유/문의 중심 |

권한 메모:

- agent도 공유 매물 생성, 문의 전송, 메시지 전송은 가능해야 한다.
- 룸 생성과 멤버 승인/거절은 owner/manager 중심이 안전하다.
- 매물 공유 수정/회수는 기본적으로 공유자 본인과 관리자만 가능해야 한다.
- 다른 사무소가 올린 공유 매물의 원본 Listing 정보는 절대 직접 노출되면 안 된다.

## 4. 핵심 시나리오

### 시나리오 A: 룸 탐색과 진입

1. 사용자는 네트워크 페이지에 들어온다.
2. 시스템은 `전체 게시판`, `내 모임`, `지역 모임`, `공동중개` 진입 탭과 참여 중인 룸, 대기 중인 룸, 공개 룸 추천을 보여준다.
3. 사용자는 먼저 보드 맥락을 고른 뒤 특정 룸을 선택해 상세 작업공간으로 들어간다.
4. 완료 조건:
   - 현재 업무에 필요한 공동중개 방으로 바로 진입할 수 있다.

### 시나리오 A-1: 공동중개 보드에서 매물 탐색

1. 사용자는 `공동중개` 보드를 연다.
2. 시스템은 `공유매물`, `구합니다` 탭과 지역/가격/면적/방수 조건 필터를 보여준다.
3. 사용자는 필터를 적용해 매물 리스트를 탐색하고 관심 매물을 연다.
4. 완료 조건:
   - 룸에 직접 들어가지 않아도 공동중개 물건을 넓게 탐색할 수 있다.

### 시나리오 B: Listing을 룸에 공유

1. 사용자는 룸 안에서 `매물 공유`를 누르거나 Listing Detail에서 `네트워크 공유`를 실행한다.
2. 시스템은 공유 가능한 Listing 목록과 공개 필드 선택 UI를 보여준다.
3. 사용자는 단지명, 가격, 면적, 담당자 연락처 등 공개 범위를 설정하고 공유한다.
4. 완료 조건:
   - 공유 매물이 룸 피드에 나타나고
   - 마스킹 규칙이 적용된다.

### 시나리오 C: 공유 매물 문의

1. 사용자는 룸 내 공유 매물 카드를 연다.
2. 시스템은 공개 가능한 정보만 보여주고 `문의하기` 액션을 제공한다.
3. 사용자는 문의 메시지를 작성해 보낸다.
4. 완료 조건:
   - NetworkInquiry가 생성되고
   - 공유자 측에 알림이 간다.

### 시나리오 D: 문의 응답과 후속 처리

1. 공유 매물 소유 사무소는 받은 문의 목록을 연다.
2. 시스템은 문의자 사무소, 메시지, 생성일, 상태를 보여준다.
3. 사용자는 `수락` 또는 `거절`을 선택하고 필요한 응답 메시지를 남긴다.
4. 완료 조건:
   - 문의 상태가 업데이트되고
   - 후속 공동중개 대화 또는 작업으로 이어진다.

### 시나리오 E: 룸 채팅과 매물 카드 연동

1. 사용자는 룸 우측 채팅 패널에서 메시지를 입력한다.
2. 시스템은 일반 텍스트 또는 공유 매물 카드 첨부 메시지를 전송한다.
3. 사용자는 채팅 흐름 속에서 특정 공유 매물로 다시 이동한다.
4. 완료 조건:
   - 메시지와 공유 매물 문맥이 끊기지 않는다.

### 시나리오 F: 룸 멤버 승인 관리

1. owner/manager는 룸의 멤버 탭을 연다.
2. 시스템은 `pending`, `approved`, `rejected`, `left` 상태의 사무소 목록을 보여준다.
3. 사용자는 참여 요청을 승인/거절하거나 기존 멤버 권한을 조정한다.
4. 완료 조건:
   - 룸 참여 상태가 명확하고
   - 승인되지 않은 사무소는 내부 매물에 접근하지 못한다.

## 6. 조회 데이터

| 항목 | 설명 | 필수 여부 | 출처 |
| --- | --- | --- | --- |
| roomList | 참여 가능/참여 중인 룸 목록 | 필수 | `GET /network/rooms` |
| selectedRoom | 선택 룸 상세 | 필수 | `GET /network/rooms/:id` |
| roomMembers | 선택 룸 멤버 목록 | 중요 | `selectedRoom.members` |
| sharedPropertyList | 선택 룸의 공유 매물 목록 | 필수 | `GET /network/rooms/:id/shared-properties` |
| boardSharedPropertyList | 공동중개 보드 전체 공유매물 목록 | 중요 | 후속 board query 필요 |
| wantedPostList | `구합니다` 탭 목록 | 중요 | future |
| sharedPropertyDetail | 특정 공유 매물 상세 | 중요 | list item expand or dedicated fetch |
| incomingInquiries | 내가 받은 문의 목록 | 중요 | room/inquiry query |
| outgoingInquiries | 내가 보낸 문의 목록 | 중요 | room/inquiry query |
| roomMessages | 선택 룸 채팅 메시지 | 중요 | `GET /network/rooms/:id/messages` |
| roomActivitySummary | 룸 최근 활동 요약 | 선택 | 후속 aggregate query 필요 |
| shareableListings | 네트워크에 공유 가능한 Listing 목록 | 중요 | Listing search projection |

조회 규칙:

- 초기 진입 시:
  - `GET /network/rooms`로 룸 목록을 조회한다.
- 룸 선택 시:
  - 룸 상세, 공유 매물, 문의 요약, 멤버 요약, 최근 메시지를 함께 불러와야 한다.
- 보드 검색 시:
  - 선택한 보드 맥락과 필터 조건으로 공유매물 또는 구함 목록을 재조회한다.
- 탭 전환 시:
  - `문의`, `멤버`, `채팅`은 lazy load 가능하다.
- 실시간 갱신:
  - 새 메시지, 새 문의, 문의 응답은 실시간 또는 짧은 polling으로 반영되는 것이 좋다.

## 7. 검색 / 필터 / 정렬

- 기본 검색 대상:
  - 보드 탭명/모임명
  - 룸명
  - 지역 태그
  - 공유 매물 단지명
  - 공유 코멘트
  - 담당자명
- 기본 정렬:
  - 룸 목록: 최근 활동순 desc
  - 공동중개 보드 리스트: 최신순 desc
  - 공유 매물: 공유일 desc
  - 문의 목록: 생성일 desc
  - 메시지: createdAt asc
- 필터 항목:
  - 보드 구분: 전체 게시판 / 내 모임 / 지역 모임 / 공동중개
  - 공동중개 하위 탭: 공유매물 / 구합니다
  - 룸 상태: 참여 중 / 대기 / 공개방
  - 룸 지역
  - 주소: 시/도 / 시군구 / 읍면동 / 단지명
  - 공유 매물 거래유형
  - 가격 범위
  - 면적 범위
  - 방 수
  - 욕실 수
  - 문의 상태: pending / accepted / rejected / expired
  - 내가 올린 매물 / 내가 문의한 매물
- 저장 가능한 뷰:
  - MVP에서는 사용자 저장 뷰 없음
- 기본 탭은 `공유 매물`, `문의`, `멤버`
- 역할별 기본 뷰 차이:
  - agent는 `공동중개 > 공유매물` 탭 진입이 자연스럽다.
  - manager/owner는 `문의` 또는 `멤버` 탭 진입이 더 유용할 수 있다.

## 8. 주요 액션

| 액션 | 설명 | 권한 | 성공 결과 | 실패/예외 |
| --- | --- | --- | --- | --- |

| 참여 요청 | 공개방 참여 신청 | 전체 | pending 멤버 생성 | 이미 참여 중 |
| 참여 승인/거절 | 멤버 요청 처리 | owner/manager | member status 갱신 | 권한 없음 |

| 매물 카드 첨부 | 채팅에 공유 매물 카드 연결 | 승인된 멤버 | 메시지에 카드 표시 | 공유 매물 비활성 |

## 9. 생성 / 수정 폼 규칙

- 필수 입력값:
  - 룸 생성 시 `name`, `type`
  - 매물 공유 시 `roomId`, `listingId`
  - 문의 생성 시 `sharedPropertyId`
  - 메시지 전송 시 `roomId`, `content`
- 기본값:
  - room.type은 `private`
  - room.isActive는 `true`
  - roomMember.status는 `pending`
  - networkInquiry.status는 `pending`
  - sharedProperty.showSiteName/showPrice/showArea는 기본 `true`
  - sharedProperty.showDong/showUnit/showFloor/showMemo/showPhotos는 기본 `false`
- 자동 계산:
  - 문의 수, 미응답 수, 최근 활동 시각은 aggregate로 계산한다.
  - 공유 매물 카드는 마스킹 설정에 따라 출력 필드를 결정한다.
- 상호 의존 필드:
  - `showUnit=true`이면 `showDong=true`가 실무상 함께 필요한 경우가 많다.
  - `showPhotos=true`면 사진 소유권/대외 공개 정책 검토가 필요하다.
  - 문의 수락 후에는 후속 대화나 Task 생성과 연결될 수 있다.
- 저장 전 검증:
  - 같은 룸에 같은 listing 중복 공유 금지
  - 비활성 listing 공유 금지
  - 자기 사무소가 올린 매물에 자기 사무소가 문의하는 것 금지
- 저장 후 후속 액션:
  - 룸 피드 재조회
  - 알림 발송
  - 필요한 경우 Task/Notification 생성

## 10. 상태값

이 페이지가 직접 다루는 상태:

- Room type
  - `public`
  - `private`
- Room active
  - `isActive=true/false`
- Room member status
  - `pending`
  - `approved`
  - `rejected`
  - `left`
- Room member role
  - `admin`
  - `member`
- Shared property status
  - `active`
  - `inactive`
- Inquiry status
  - `pending`
  - `accepted`
  - `rejected`
  - `expired`

상태 전이 규칙:

```text
roomMember: pending -> approved | rejected -> left
inquiry: pending -> accepted | rejected | expired
sharedProperty: active -> inactive
```

상태별 UI 차이:

- `pending` 문의:
  - 수락/거절 CTA 노출
- `accepted` 문의:
  - 후속 대화/공동중개 연결 강조
- `rejected` 문의:
  - 읽기 전용 응답 표시
- `expired` 문의:
  - 재문의 유도
- `pending` 멤버:
  - owner/manager에게 승인 배지 노출

## 11. 예외 / 빈 상태 / 오류 상태

- 빈 상태:
  - 참여 중인 룸이 없으면 `공개방 찾기`와 `방 만들기`를 노출
- 검색 결과 없음:
  - 룸 검색, 공유 매물 검색 각각 별도 empty state 필요
- 권한 없음:
  - 승인되지 않은 룸은 읽기 전용 요약만 보여주거나 접근 차단
- 연동 실패:
  - 메시지 전송 실패, 문의 응답 실패 시 재시도 필요
- 삭제 불가 조건:
  - 활성 문의가 남아 있는 공유 매물은 즉시 완전 삭제보다 비활성화가 안전
- 충돌 상태:
  - 문의를 동시에 두 사용자가 응답한 경우 stale state 재조회 필요
- 보안 리스크:
  - 마스킹되지 않아야 할 필드가 노출되면 안 된다

## 13. Desktop 전용 요구사항

- 다중 패널 필요 여부:
  - 높음
  - 룸 목록, 공유 매물/문의, 채팅이 동시에 보여야 한다.
- 키보드 단축키:
  - `/` 룸/매물 검색 포커스
  - `Enter` 선택 룸 진입
  - `Cmd/Ctrl + Enter` 메시지 전송
- 실시간 업데이트:
  - 채팅, 문의 생성, 문의 응답, 멤버 승인 상태는 실시간 반영이 중요하다.
- 알림 연동:
  - 새 문의, 문의 응답, 룸 참여 요청은 Notification과 연결돼야 한다.
- 시스템 트레이/OS 이벤트 연동:
  - 필수는 아님
- 로컬 기능 연동:
  - 필요 없음
- 멀티 선택 / 벌크 액션:
  - MVP 제외
- 창 크기 변화 대응:
  - 좁은 폭에서는 우측 채팅 패널을 접을 수 있어야 한다.

## 14. 감사 추적 / 로그

- ActivityLog 기록 대상 액션:
  - 룸 생성
  - 룸 참여 요청/승인/거절
  - 매물 공유/수정/회수
  - 문의 생성/응답
  - 메시지 전송
- actor / source 규칙:
  - desktop 수동 조작은 `actor=user`, `source=web` 또는 desktop source 확장 필요
- 중요 감사 이벤트:
  - 민감 필드 공개 범위 변경
  - 문의 수락/거절
  - 룸 멤버 승인/퇴출

## 15. 비기능 요구사항

- 초기 로딩 목표:
  - 보드 첫 진입과 룸 목록, 선택 룸 첫 피드가 2초 이내 체감 로딩
- 대량 데이터 처리 방식:
  - 메시지와 공유 매물은 pagination 또는 infinite scroll 필요
- 낙관적 업데이트 여부:
  - 메시지 전송은 제한적 낙관 업데이트 가능
  - 문의 응답과 공유 설정 변경은 서버 응답 후 확정이 안전하다
- 오프라인/재시도 전략:
  - 메시지/문의 실패 시 draft 보존과 재시도 필요
- 접근성/가독성 메모:
  - 공유 매물 카드에서 마스킹된 필드와 비공개 필드는 시각적으로 구분돼야 한다.
  - 문의 상태 배지는 색상 외 텍스트도 함께 보여야 한다.
  - 공동중개 보드의 검색 조건은 데스크톱에서 한 화면에 보여도 과밀해 보이지 않도록 그룹화가 필요하다.

## 18. 열린 질문

- 네트워크 룸은 지역 중심으로 운영할지, 주제/거래유형 중심도 허용할지?
- `구합니다`는 BuyerRequirement와 직접 연결할지, 네트워크 전용 글로 분리할지?

- 문의 수락 후 자동으로 별도 1:1 채널을 만들지, 기존 룸 채팅 안에서 계속할지?
- 공동중개가 성사된 경우 `Deal`과 `partnerBroker` 구조로 자동 연결할지?
- 공개방 참여 승인 정책을 방마다 다르게 둘지?

## 19. 수용 기준

- 사용자는 이 페이지에서 `참여 중인 네트워크 룸을 찾고 들어가는 것`을 빠르게 할 수 있어야 한다.
- 사용자는 최소 입력으로 `내 Listing을 원하는 룸에 공유`할 수 있어야 한다.
- 사용자는 공유 매물에 대해 `문의 생성과 응답 처리`를 한 화면 체계 안에서 할 수 있어야 한다.
- 사용자는 룸 채팅과 공유 매물 문맥을 함께 볼 수 있어야 한다.
- 마스킹 정책은 UI와 API 모두에서 일관되게 지켜져야 한다.
- 예외 상황에서 사용자는 왜 공유/문의/응답이 실패했는지 이해할 수 있어야 한다.
