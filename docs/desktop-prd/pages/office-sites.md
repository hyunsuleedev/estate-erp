현재 결정:

- 이 문서는 desktop의 `관리단지 페이지`를 기준으로 작성한다.
- `OfficeSite`는 전체 단지 마스터가 아니라 `사무소가 운영상 구독·관리하는 단지 목록`이다.
- 즐겨찾기는 구독 자체의 의미가 아니라 `OfficeSite.isFavorite`로 관리하는 별도 표시 속성이다.
- 따라서 이 페이지는 `전체 Site 검색 화면`이 아니라 `사무소별 단지 운영 허브`로 봐야 한다.
- 현재 구현은 `좌측 관리단지 목록 + 중앙 호실 테이블/배치표 + 호실 상세 팝업` 구조다.
- 다만 PRD 기준 목표 UX는 `호수 클릭 -> 전용 호실 상세페이지`를 여는 흐름으로 본다.
- 이 페이지에는 `점유상태 뷰`와 `만기/변동 추적 뷰`가 추가될 수 있어야 한다.
- 이 페이지에서는 호실 row 또는 배치표 셀 클릭 문맥에서 `등기부등본 발급`을 시작할 수 있어야 한다.
- 발급된 등기부등본은 단지/동/호 기준으로 다시 조회하고 관리할 수 있어야 한다.
- 한 사무소가 발급한 등기 정보는 공용 서버에 정규화 저장하고, 다른 사무소는 일정 기간 동안 `재발급 없이 보기 전용`으로 재사용할 수 있어야 한다.
- 따라서 `원본 발급본`과 `공용 열람용 등기 스냅샷`을 구분한다.
- 관리단지에 추가하는 대상은 현재 `isPublic = true`인 중앙 Site 검색 결과가 중심이다.
- 장기적으로는 `공개 Site 추가`뿐 아니라 `사무소 전용 비공개 Site 직접 생성` 흐름도 필요할 수 있다.
- `점유상태 뷰`는 우선 외부 추정 없이 `내부 CRM 데이터`만으로 표시한다.
- `점유상태 추정 알고리즘`은 별도 연구/설계가 필요한 후속 주제로 두고 현재 문서에서는 구현 우선순위를 낮춘다.
- 반면 `만기/변동` 뷰는 주 취급단지 대상 외부 데이터/빅데이터 알림 성격이 강하다.
- `등기 공용 캐시`는 발급 비용 절감과 중복 발급 방지를 위한 핵심 정책으로 본다.
- `만기 AI 알림`은 국토교통부 실거래가의 임대차 계약일을 기준으로 만기 도래 가능성을 탐지하는 기능으로 정의한다.
- `등기변동 알림`은 인터넷등기소 기준의 변동 이력을 수집하여 소유권이전, 근저당권설정, 압류, 가압류 등의 변동이 발생했을 때 알려주는 기능으로 정의한다.
- `거래 AI 알림`은 주 취급단지의 자체 보유 빅데이터를 활용해 실거래 계약일, 실거래가, 평형/라인 유사군 변동을 알려주는 시세/거래 신호 기능으로 정의한다.
- 따라서 이 알림 기능들은 별도 수집 파이프라인과 규칙 엔진을 전제로 한다.

## 1. 페이지 목적

- 이 페이지가 해결해야 하는 핵심 업무:
  - 사무소가 자주 다루는 단지들을 모아 빠르게 접근한다.
  - 단지 내부의 동/호실, 소유자, 세입자, 매물, 상담 기록을 운영 관점으로 본다.
  - 단지를 기준으로 매물 등록과 후속 상담 흐름을 시작한다.
  - 필요한 호실의 등기부등본을 즉시 발급하고 발급 이력을 관리한다.
  - 이미 유효한 공용 등기 스냅샷이 있으면 재발급하지 않고 우선 활용한다.
  - 단지별 점유상태와 외부 변동 신호를 빠르게 파악한다.
- primary 사용자:
  - agent
- secondary 사용자:
  - manager, owner
- 이 페이지가 필요한 이유:
  - 전체 Site 마스터는 너무 넓고, 실무는 특정 단지 반복 접근이 많다.
  - 중개사는 `래미안고덕`, `고덕그라시움` 같은 주력 단지의 호실 현황을 빨리 훑어야 한다.
  - desktop에서는 단지 기준 탐색, 호실별 운영, 매물 등록 연결이 한 화면에서 이뤄지는 것이 효율적이다.

## 2. 사용 시점

- 사용자가 이 페이지에 들어오는 대표 상황:
  - 특정 관리단지의 호실 현황을 확인할 때
  - 소유자/세입자/상담 이력이 있는 호실을 찾을 때
  - 새 호실을 추가하거나 동을 추가할 때
  - 특정 호실에서 바로 매물 등록을 시작할 때
  - 특정 동/호의 등기부등본을 바로 발급할 때
  - 과거에 발급한 등기부등본을 다시 열거나 비교할 때
  - 특정 단지의 자가/전세/월세 점유 분포를 볼 때
  - 곧 만기 도래 가능성이 높은 임대차와 권리 변동 발생 호실을 추적할 때
- 진입 경로:
  - 사이드바 `관리단지`
  - Properties/New의 단지 선택 전후 역이동
  - Contacts/Consultations에서 해당 단지 역진입
- 이전 화면:
  - Properties/New
  - Contacts
  - Consultations
  - Listings
- 다음 화면:
  - Unit Detail Page
  - Property/New
  - 관련 Contact / Listing 화면
- 이 페이지를 나가는 대표 액션:
  - 관리단지 선택
  - 호실 열기
  - 매물 등록
  - 단지 추가/제거

## 3. 사용자 역할과 권한

| 역할 | 조회 | 생성 | 수정 | 삭제 | 승인/확정 | 비고 |
| --- | --- | --- | --- | --- | --- | --- |
| owner | 전체 조회 | 가능 | 가능 | 가능 | 가능 | 사무소 운영 기준 관리 |
| manager | 전체 조회 | 가능 | 가능 | 가능 | 가능 | 주력 단지 운영 관리 |
| agent | 전체 조회 | 가능 | 가능 | 제한적 | 가능 | 현장 운영 중심 |

권한 메모:

- OfficeSite 조회는 office 전체 기준으로 허용한다.
- agent도 관리단지 추가와 호실 탐색은 가능해야 한다.
- 같은 사무소에서 발급한 등기부등본은 office 구성원이 함께 본다.
- 다른 사무소가 발급한 정보는 공용 스냅샷이 유효한 기간에만 `보기 전용`으로 재사용한다.
- 관리단지 제거는 owner/manager 중심이 더 안전할 수 있다.
- 중앙 공공 Site 자체 수정/삭제는 금지되어야 한다.
- OfficeSite는 제거 가능하더라도, 원본 Site가 중앙 데이터인 경우 Site 자체는 삭제되면 안 된다.

## 4. 핵심 시나리오

### 시나리오 A: 관리단지 추가

1. 사용자는 `단지 추가`를 누르고 중앙 Site를 검색한다.
2. 시스템은 공개 Site 중 단지명/주소 기준 검색 결과를 보여준다.
3. 사용자는 원하는 단지를 선택해 OfficeSite로 추가한다.
4. 완료 조건:
   - 단지가 사무소의 관리단지 목록에 들어오고
   - 이후 빠르게 접근 가능하다.

### 시나리오 B: 단지 내부 호실 탐색

1. 사용자는 좌측 목록에서 관리단지를 선택한다.
2. 시스템은 해당 Site의 동/호실/소유자/세입자/매물/상담 요약을 불러온다.
3. 사용자는 동/타입/호수/상담 키워드로 필터링한다.
4. 완료 조건:
   - 단지 내부 운영 현황을 빠르게 파악할 수 있다.

### 시나리오 C: 배치표 기반 확인

1. 사용자는 `배치표` 뷰로 전환한다.
2. 시스템은 floor + lineNo 기반으로 호실 그리드를 그린다.
3. 사용자는 매물 존재, 상담 존재, 선택 상태를 시각적으로 확인한다.
4. 완료 조건:
   - 복잡한 단지에서도 공간 구조를 직관적으로 이해할 수 있다.

### 시나리오 D: 호실 상세와 후속 작업

1. 사용자는 호실 리스트에서 특정 `호수`를 클릭한다.
2. 시스템은 전용 `호실 상세페이지`를 열고, 해당 호실의 기본 정보, 소유자/세입자, 매물, 상담, 등기 문서를 함께 보여준다.
3. 사용자는 여기서 바로 `매물 등록`, `소유자/세입자 확인`, `상담 추가`, `등기부등본 발급`을 시작한다.
4. 완료 조건:
   - 호실 단위 운영 정보가 한 곳에 모이고
   - 후속 실무로 자연스럽게 이어진다.

### 시나리오 E: 점유상태 뷰 확인

1. 사용자는 `점유상태` 뷰로 전환한다.
2. 시스템은 내부 CRM 데이터만 사용해 각 호실을 `자가`, `전세`, `월세`, `공실/미상` 상태로 분류한다.
3. 사용자는 `자가/전세/월세/공실·미상`만 골라 본다.
4. 완료 조건:
   - 단지의 점유 분포를 빠르게 파악할 수 있다.

### 시나리오 F: 만기/변동 추적

1. 사용자는 `만기/변동` 뷰 또는 패널을 연다.
2. 시스템은 관리단지 전체에서 `만기 AI 알림`, `등기변동 알림`, `거래 AI 알림`을 표로 보여준다.
3. 사용자는 특정 항목을 열어 해당 호실/단지로 이동하거나 후속 작업을 만든다.
4. 완료 조건:
   - 관리단지 전체의 변동 리스크를 날짜 기준으로 관리할 수 있다.

### 시나리오 G: 등기부등본 발급

1. 사용자는 테이블 row 또는 배치표 셀에서 특정 동/호를 선택한다.
2. 시스템은 해당 호실의 단지명, 동, 호, 주소 문맥을 확인한 뒤 `등기부등본 발급` 액션을 노출한다.
3. 사용자는 발급 유형을 선택하고 발급을 실행한다.
4. 시스템은 발급 결과 PDF와 메타데이터를 저장하고, 해당 호실의 문서 목록에 즉시 반영한다.
5. 완료 조건:
   - 사용자는 호실 문맥에서 등기부등본을 발급할 수 있고
   - 발급본이 다시 열람 가능한 상태로 저장된다.

### 시나리오 H: 발급한 등기부등본 관리

1. 사용자는 호실 상세 또는 `등기 문서` 패널에서 과거 발급본 목록을 본다.
2. 시스템은 발급일, 발급 유형, 최신 여부, 파일 열기/다운로드 액션을 보여준다.
3. 사용자는 최신본을 열거나 오래된 발급본을 비교/정리한다.
4. 완료 조건:
   - 같은 호실의 발급 이력을 누적 관리할 수 있다.

### 시나리오 I: 다른 사무소가 발급한 등기 정보 재사용

1. 사용자는 특정 동/호에서 `등기부등본 발급` 또는 `등기 정보 보기`를 시도한다.
2. 시스템은 먼저 공용 서버에서 해당 호실의 유효한 `RegistrySnapshot`이 있는지 확인한다.
3. 유효 기간 안의 스냅샷이 있으면 사용자는 재발급 비용 없이 내용을 `보기 전용`으로 확인한다.
4. 유효 기간이 지났거나 정보가 오래되었으면 새 발급을 유도한다.
5. 완료 조건:
   - 다른 사무소가 먼저 발급한 정보도 일정 기간 동안 재사용할 수 있다.

### 시나리오 J: 거래 AI 알림 확인

1. 사용자는 `거래 AI 알림` 패널을 연다.
2. 시스템은 동일 단지/동/호/평형 또는 유사군 기준으로 최근 실거래 계약일과 실거래가 변동을 요약해 보여준다.
3. 사용자는 이를 보고 집주인 컨택, 시세 점검, 매물화 작업을 시작한다.
4. 완료 조건:
   - 단지의 거래 온도와 접촉 타이밍을 빠르게 읽을 수 있다.

## 5. 화면 구조

예시:

- 좌측: 관리단지 목록
- 중앙: 선택 단지의 호실 운영 화면
- 별도 화면: 선택 호실 상세

실제 정의:

- 좌측 사이드바:
  - 관리단지 검색
  - 그룹 기준 전환
    - `전체`
    - `지역`
    - `유형`
  - 관리단지 목록
  - `단지 추가` 버튼
- 중앙 메인 영역:
  - 상단 filter bar
    - 동 multi-select
    - 타입 multi-select
    - 호수 검색
    - 상담내역 검색
    - 필터 초기화
    - view mode toggle
      - `테이블`
      - `배치표`
      - `점유상태`
      - `만기/변동`
  - 본문
    - `테이블 뷰`
      - 호실 단위 표
    - `배치표 뷰`
      - 동별 floor × lineNo 그리드
    - `점유상태 뷰`
      - 호실 셀을 점유 유형별로 색상/패턴 구분
      - 상단 quick filter
        - `자가`
        - `전세`
        - `월세`
        - `공실/미상`
      - 초기 버전은 내부 CRM 데이터 기준으로만 계산
    - `만기/변동 뷰`
      - `만기 AI 알림`
      - `등기변동 알림`
      - `거래 AI 알림`
      - 각 섹션은 별도 표 또는 카드형 리스트
  - 빈 상태:
    - 단지 미선택 시 안내 화면
- 호실 상세페이지:
  - 진입 방식:
    - 호실 리스트 row의 `호수` 셀 클릭

  - 동/호수
  - 타입명
  - 전용면적 / 공급면적
  - 층 / 라인
  - 필로티 여부
  - 점유상태
- `소유자`
  - 대표 소유자
  - 공동 소유자 목록
  - 각 연락처의 이름, 전화번호, 지분율, 실거주 여부, 메모
  - `연락처 상세 열기`
- `세입자`
  - 현재 세입자 목록
  - 이름, 전화번호, 보증금, 월세, 계약 시작일, 계약 종료일, 퇴거 예정일, 상태
  - `세입자 연락처 열기`
- `등록 매물`
  - 현재/과거 매물 목록
  - 거래유형, 가격/보증금/월세, check status, 최근 수정일

  - `새 매물 등록`
- `등기 문서`
  - 같은 사무소가 발급한 등기부등본 목록

  - 발급일, 발급 사무소, 공유 만료일, 열기 액션
- `상담내역`
  - 최신순 타임라인
  - 여러 줄 메모 그대로 표시
  - 각 상담의 작성자, 작성일, 연결 연락처/매물 정보
  - 스크롤 가능
- `후속 작업`
  - 이 호실/Property에 연결된 Task 목록
  - due date, 상태, 담당자
- `최근 활동 로그`
  - 매물 등록/가격수정/소유자변경/세입자변경/등기발급 같은 이벤트 표시

점유상태 셀 표시 규칙:

- `자가`
  - 내부 CRM에서 소유자 거주 신호가 있는 경우
- `전세`
  - 내부 CRM에서 세입자 정보가 있고 월세 금액이 없는 경우
- `월세`
  - 내부 CRM에서 세입자 정보가 있고 월세 금액이 있는 경우
- `공실/미상`
  - 내부 CRM 기준 유의미한 점유 신호가 없음

점유상태 판단 우선순위:

- 내부 CRM 확정 데이터
  - PropertyContact.isResident, Tenant.status, Tenant.monthlyRent
- 신호 없음
  - 공실/미상

조회 규칙:

- 초기 진입 시:
  - `GET /office-sites`로 관리단지 목록을 조회한다.
- 관리단지 선택 시:
  - `GET /sites/:id`로 상세를 불러온다.
- 호실 상세페이지 진입 시:
  - 선택한 `unitId` 기준으로 property, 소유자, 세입자, 매물, 상담, 등기 문서를 함께 조회해야 한다.
- 단지 추가 검색 시:
  - 2글자 이상일 때 중앙 Site 검색을 호출한다.
- 후속 개선:
  - 현재 Site detail payload가 무거우므로, 호실 수가 큰 단지는 pagination/partial fetch가 필요할 수 있다.
  - 등기 문서는 `원본 발급본`과 `공용 스냅샷`을 분리 조회하는 것이 안전하다.

## 7. 검색 / 필터 / 정렬

- 기본 검색 대상:
  - 좌측 목록: 단지명, 도로명주소, 지번주소
  - 중앙 호실: 호수명, 상담내용, 상담자명, 상담자 전화번호
- 기본 정렬:
  - 관리단지 목록: createdAt desc
  - 호실 목록: 동, 층, 호수 기본 정렬
- 필터 항목:
  - 관리단지 그룹: 전체/지역/유형
  - 동
  - 타입
  - 호수 키워드
  - 상담 키워드
  - 등기문서 발급 여부
  - 공용 스냅샷 존재 여부

  - 최근 발급일
  - 점유상태: 자가/전세/월세/공실
  - 만기 임박 여부
  - 권리변동 유형
  - 거래 알림 유형
- 저장 가능한 뷰:
  - MVP에서는 사용자 저장 뷰 없음
  - 기본 제공 뷰는 `테이블`, `배치표`, `점유상태`, `만기/변동`

  - agent는 `배치표`와 `테이블`을 모두 자주 사용
  - manager/owner는 `테이블`이 운영 점검에 유리

## 9. 생성 / 수정 폼 규칙

- 필수 입력값:
  - OfficeSite 추가 시 `siteId`
  - Dong 추가 시 `siteId`, `name`
  - Unit 추가 시 `siteId`, `name`
- 기본값:
  - OfficeSite memo는 비어 있어도 된다
  - Unit 추가 시 동 미선택 허용 가능
- 자동 계산:
  - 배치표에서는 `floor`, `lineNo`, `name`을 기반으로 위치 계산
  - `Unit.name` 숫자를 fallback으로 파싱해 floor/lineNo를 추론한다
  - 점유상태는 내부 CRM 데이터만으로 계산한다
- 상호 의존 필드:
  - 동이 존재하는 단지는 Unit 생성 시 dong 선택이 권장된다
  - 단지 타입/평형 체계가 있으면 UnitType과 면적을 연결하는 구조가 장기적으로 필요하다
  - 등기부등본 발급은 `site`, `dong`, `unit`, 주소 표준화 값이 정확해야 한다
  - 공용 스냅샷은 `snapshotCreatedAt`, `sharedUntil`, `sourceIssueOfficeId`, `isViewOnly` 같은 정책 필드가 필요하다
  - `만기 AI 알림`은 임대차 계약일, 거래유형, 만기 추정 규칙이 중요하다
  - `등기변동 알림`은 등기 이벤트 타입 정규화가 중요하다
  - `거래 AI 알림`은 실거래가/계약일/유사군 매핑 정확도가 중요하다
- 저장 전 검증:
  - 중앙 Site를 OfficeSite에 추가할 때 접근 가능 여부 확인
  - 이름 공백 금지
  - 면적은 숫자여야 한다
- 저장 후 후속 액션:
  - 해당 단지 상세 재조회
  - 목록/검색 캐시 갱신
  - 등기부등본 발급 성공 시 해당 호실의 문서 목록 재조회
  - 새 발급 성공 시 공용 등기 스냅샷 upsert

현재 구현 메모:

- OfficeSite memo 수정 API는 있으나 desktop UI는 아직 없다.
- 단지 추가는 중앙 Site 검색 기반이며, `사무소 전용 Site 직접 생성` UI는 없다.
- 호실 수정/삭제 액션은 팝업 메뉴에 있으나 실제 동작은 아직 연결되지 않았다.
- 호실 기준 등기부등본 발급/관리 기능은 아직 구현되어 있지 않다.
- 타 사무소 재사용용 공용 등기 스냅샷 저장소도 아직 구현되어 있지 않다.
- 점유상태 뷰와 만기/변동 뷰는 아직 구현되어 있지 않다.
- `점유상태 뷰`의 초기 버전은 별도 외부 파이프라인 없이 내부 CRM 데이터만으로 구현 가능하다.
- `만기 AI 알림`, `등기변동 알림`, `거래 AI 알림`은 별도 데이터 수집/정제 파이프라인이 필요하다.
- `점유상태 추정 알고리즘`은 우선순위를 낮추고, 나중에 외부 데이터 결합 단계에서 검토한다.

## 10. 상태값

이 페이지가 직접 다루는 상태:

- OfficeSite는 별도 business status가 없다.
- Site.type
  - `apartment`
  - `officetel`
  - `villa`
  - `house`
  - `commercial`
  - `land`
  - `living_accommodation`
- Unit 운영 상태는 직접 저장하지 않고 연결 데이터로 표현된다.
  - 매물 있음
  - 상담 있음
  - 소유자/세입자 있음
- 호실 점유상태(derived)
  - `owner_occupied`
  - `jeonse`
  - `monthly`
  - `vacant_or_unknown`
- 알림 타입(derived/future)
  - `lease_expiry`
  - `registry_change`
  - `trade_signal`
- 등기문서 상태(future)
  - `issuing`
  - `issued`
  - `failed`
  - `archived`
- 공용 스냅샷 상태(future)
  - `fresh`
  - `stale`
  - `expired`

상태 전이 규칙:

```text
OfficeSite는 status 전이보다 `추가 -> 운영 -> 제거` 흐름에 가깝다.
```

상태별 UI 차이:

- 선택된 관리단지:
  - 좌측 목록 active style
- 배치표 셀:
  - 매물 있음: 강조 색상
  - 상담 있음: 보조 강조 색상
  - 선택됨: primary 강조
- 점유상태 셀:
  - 자가/전세/월세/공실을 색상과 패턴으로 구분
  - 초기 버전은 내부 데이터 기준이므로 `미상` 표기가 분명해야 한다

## 11. 예외 / 빈 상태 / 오류 상태

- 빈 상태:
  - 관리단지가 없으면 좌측 목록에 empty state와 `단지 추가` 유도 필요
- 검색 결과 없음:
  - 단지 검색 또는 중앙 Site 검색 모두 별도 안내 필요
- 권한 없음:
  - 제거/수정 액션 비활성화
- 연동 실패:
  - siteDetail 로드 실패 시 재시도 안내 필요
  - 등기부등본 발급 실패 시 원인 코드와 재시도 액션이 필요하다
  - 공용 스냅샷이 있어도 원본과 시점 차이가 크면 `참고용` 표시가 필요하다
- 삭제 불가 조건:
  - OfficeSite 제거는 가능하더라도, 원본 Site 삭제와 혼동되면 안 된다
- 충돌 상태:
  - 다른 사용자가 동/호수를 추가한 경우 상세 재조회 필요
- 구조 한계:
  - 현재 호실 운영은 Site detail 한 번에 많이 가져오므로 대형 단지에서 무거울 수 있다
  - 현재는 점유상태 이력 스냅샷이 없어 과거 변동 추적은 약하다
  - 등기부등본 원본 파일 저장소와 메타데이터 모델이 아직 없다
  - 공용 스냅샷의 TTL, 갱신 주기, 타 사무소 열람 범위 정책이 아직 없다
  - 만기/등기/거래 알림은 외부 수집 파이프라인 없이는 생성할 수 없다

## 13. Desktop 전용 요구사항

- 다중 패널 필요 여부:
  - 높음
  - 좌측 단지 목록 + 중앙 운영 뷰 + 호실 상세 팝업 구조가 핵심이다
- 키보드 단축키:
  - `/` 단지 또는 호실 검색 포커스
  - `Enter` 선택 항목 열기
  - `Cmd/Ctrl + K` 단지 추가 검색으로 연결 가능하면 좋다
- 실시간 업데이트:
  - 동/호수/매물/상담이 다른 화면에서 바뀌면 재조회 또는 invalidation 필요
- 알림 연동:
  - 직접적 필요는 낮음
- 시스템 트레이/OS 이벤트 연동:
  - 필요 없음
- 로컬 기능 연동:
  - PDF 뷰어 오픈
  - 다운로드 파일 열기
- 멀티 선택 / 벌크 액션:
  - MVP 제외
- 창 크기 변화 대응:
  - 사이드바 접기/펼치기 필요
  - 좁은 폭에서는 배치표보다 테이블 뷰가 안정적
  - 점유상태 legend와 alert table이 좁은 폭에서 깨지지 않아야 한다

  - 호실 구조 변경

## 15. 비기능 요구사항

- 초기 로딩 목표:
  - 관리단지 목록 200개 기준 2초 이내 체감 로딩
- 대량 데이터 처리 방식:
  - 목록은 OfficeSite 경량 projection 유지
  - 상세는 단지 규모에 따라 분할 fetch 검토 필요
- 낙관적 업데이트 여부:
  - 관리단지 추가/제거는 제한적 가능
  - 동/호수 추가는 서버 성공 후 재조회가 안전하다
- 오프라인/재시도 전략:
  - 추가/제거 실패 시 에러 피드백과 재시도 가능해야 한다
- 접근성/가독성 메모:
  - 배치표에서 색상만으로 상태를 구분하지 않도록 보조 표식 필요
  - 단지명과 주소는 긴 경우 잘려도 hover/context로 확인 가능해야 한다
  - 점유상태 legend가 항상 보여야 한다
  - 만기/변동 표는 날짜 기준 정렬이 명확해야 한다
  - 등기 문서 목록은 최신본과 과거본이 헷갈리지 않도록 발급일/최신 badge가 분명해야 한다
  - 공용 스냅샷은 `발급 사무소`, `발급일`, `공유 만료일`, `보기 전용` 표기가 분명해야 한다

## 19. 수용 기준

- 사용자는 이 페이지에서 `자주 다루는 단지를 빠르게 찾고 선택`할 수 있어야 한다.
- 사용자는 선택한 단지에서 `호실, 소유자, 세입자, 매물, 최근 상담`을 한 번에 파악할 수 있어야 한다.
- 사용자는 `테이블`과 `배치표` 두 관점으로 단지를 운영할 수 있어야 한다.
- 사용자는 `점유상태` 뷰에서 자가/전세/월세/공실 분포를 빠르게 볼 수 있어야 한다.
- 사용자는 `만기/변동` 뷰에서 곧 만기되는 호실과 후속 관리 대상을 추적할 수 있어야 한다.
- 사용자는 특정 동/호에서 바로 `등기부등본 발급`을 시작하고, 과거 발급본을 다시 열 수 있어야 한다.
- 사용자는 다른 사무소가 최근 발급한 등기 정보가 있으면 일정 기간 동안 재발급 없이 `보기 전용`으로 활용할 수 있어야 한다.
- 사용자는 호수 클릭만으로 `소유자, 세입자, 매물, 상담, 등기 문서`가 모인 전용 상세페이지로 들어갈 수 있어야 한다.
- 사용자는 특정 호실에서 바로 `매물 등록` 같은 후속 업무로 이동할 수 있어야 한다.
- OfficeSite와 Site의 개념 차이가 UI와 데이터 구조에서 혼동되지 않아야 한다.
