# Estate ERP Decisions

이 문서는 현재 확정된 선택과 미결정 사항을 정리한다. 제품 범위는 [prd.md](./prd.md), 구조 설명은 [ARCHITECTURE.md](./ARCHITECTURE.md)를 본다.

## 1. 현재 확정된 결정

| 항목 | 결정 | 이유 |
|------|------|------|
| 백엔드 | NestJS | 서버 로직과 MCP/CTI 연계 제어가 필요 |
| DB | PostgreSQL + Prisma | 타입 안전성과 스키마 통제 |
| 실시간 | Socket.io | CTI와 팀 동기화에 유리 |
| 큐/잡 | Redis + BullMQ | 규칙 엔진과 백그라운드 작업 |
| 데스크톱 | Electron | 설치형 UX와 로컬 기능 필요 |
| 웹 | Vite SPA | 보조 접근 채널 |
| 모바일 | React Native Android only | 전화 감지/녹음 제약 대응 |
| AI 전략 | 내장 안 함 | MCP로 외부 AI 연결 |
| MCP 전략 | CRM MCP Server 우선 | AI 친화적 시스템으로 설계 |
| agent 업무 단위 | 독립 `AgentActionRequest`, 예외만 `Task` 승격 | 일반 직원 업무와 고빈도 AI 검토함을 분리 |
| 광고 자동화 MVP | 승인 후 `computer-use-v1` 실행 + 이실장 저장값 검증 | 저장 후 같은 광고를 reload해 persisted 값을 확인하고 네이버 재관측은 하지 않음 |
| 내 광고 원장 | `ListingAdvertisement` + 정확한 Listing/Unit 귀속 | CP가 상세 주소를 제공하므로 별도 호실 연결·제외 상태가 불필요 |
| CP 광고 상태 | row는 `active/ended`, 수집 실패는 `AdvertisementSyncRun/Step` | CP 조회는 현재 광고만 반환하며 실행 오류를 개별 광고 상태로 만들지 않음 |
| 광고 식별자 | channel/externalAdId/url=CP, naverArticleNo/naverUrl=네이버 | CP 제출 원장과 네이버 비교 대상을 혼동하지 않음 |
| 외부 effect 승인 | exact contentHash 필수 | 사람이 본 변경안과 실제 실행 명령의 불일치 차단 |
| CTI 연동 | 별도 브리지 프로세스 | 32비트 SDK 제약 |
| 스크래핑 실행 위치 | 사용자 로컬 우선 | 세션, IP, 법적 리스크 대응 |
| CP 로그인 자격증명 | Electron OS 보안 저장소 + 기기 전용 로컬 MCP | 서버·Prisma에는 비밀번호를 저장하지 않고 로컬 runner에는 로그인 준비 결과만 제공 |
| 주소 체계 | 법정동코드 + 도로명 + 지번 | 외부 시스템 연동 대비 |
| 멀티테넌시 | `office_id` 기반 분리 | SaaS 격리 기본 전제 |
| 킬러 피쳐 | 공동 중개 네트워크 | 네트워크 효과와 락인 |

## 2. 현재 제품 원칙

- CRM 코어를 먼저 완성한다.
- 데이터 구조를 먼저 바로잡고 UI는 그 위에 얹는다.
- AI는 승인/감사 가능한 구조로만 붙인다.
- 데스크톱은 메인, 웹은 보조 채널로 본다.
- 외부 연동은 “서버가 대신 해주는 구조”보다 “사용자 로컬에서 안전하게 실행되는 구조”를 우선한다.
- 범용 AI 제안함을 만들지 않고 capability별 단일 외부 부작용만 승인한다.
- provider computer use는 보이는 로컬 세션, exact-hash 승인, 즉시 중단,
  persisted-state 재확인 조건으로 실행한다.

### 데스크톱 탭 UX — 탭 전환 상태 보존 (지연)

**현재 상태**: 데스크톱은 단일 라우터 + 활성 탭 1개 모델. 탭 전환 = 라우터 navigate. 비활성 탭의 React tree는 unmount되고 다시 활성화되면 재마운트되어 리렌더 + API 재요청이 발생. TanStack Query 1분 staleTime + URL search params 보존이 일부 흡수.

**관찰된 한계**:
- 매물 등록·계약서 작성 같은 긴 폼은 탭 전환 시 입력값 손실 위험.
- 매물 목록 같은 데이터 페이지는 스크롤 위치 손실.
- 다이얼로그/인라인 편집/위저드/마스터-디테일 등 ERP 폼 패턴이 다양해 일률적 보존이 어려움.

**검토한 모델**:
- **VSCode 모델 (옵션 Z, 상태 보존)**: 탭은 메타만. 활성 탭만 React tree. 입력/스크롤/필터 등을 zustand·URL·persist에 보존해 "보존된 것처럼" 보이게.
- **Notion 모델 (옵션 A, WebContentsView 분리)**: 탭마다 별도 Chromium 컨텍스트. 진짜 메모리 보존 + 백그라운드 작업. 비용이 비대칭으로 큼 (TabController 102메서드급, 신규 라우트 추가마다 IPC/state slice 추가, 탭 1개당 50~150MB).
- **Chrome 모델**: 탭=프로세스 + 시간 기반 hibernate. 일반 웹사이트에 적합, 같은 앱의 다른 화면인 ERP에 안 맞음.

**결정**:
- **Notion 모델은 채택하지 않음**. 1인 개발팀 영구 유지보수 비용이 도메인 가치를 정당화하지 못함. 사용자 RAM 8~16GB 혼재 환경에서 메모리 1GB+ 점유는 위험.
- **VSCode 모델(옵션 Z) 방향으로 가되, 모든 폼 페이지가 구현 완료된 후에 적용**. 미리 추상화하면 안 쓰는 페이지의 보존 로직 유지비만 증가.
- **단계 구분**:
  - 레벨 1 (공짜로 보존): TanStack Query 캐시, URL search params — 이미 동작 중.
  - 레벨 2 (작은 비용): 라우트별 스크롤 위치 보존 hook 1개로 전 페이지 적용.
  - 레벨 3 (페이지별 명시 작업): 매물 등록·계약서 작성 등 위저드형 폼만 zustand `persist`로 draft 보존.
- **트리거**: 폼 페이지가 모두 구현되어 패턴이 굳어지고, 사용자 베타에서 "어디서 가장 입력이 사라져 화났는지" 데이터가 모인 시점. 그때 레벨 2부터 일괄 적용 → 레벨 3는 상위 3~5개 페이지만.

**관련 결정**:
- 데스크톱 탭은 Chrome 스타일(타이틀바 안 inline, 사이드바 깨뜨리지 않음)로 채택.
- 탭 detach는 VSCode 스타일 ghost-window(마우스 따라다니는 새 창)로 채택.
- 떼어낸 창도 메인 창과 동일한 사이드바+탭바 구조 (윈도우별 독립 탭 풀, 데이터는 cross-window invalidate).

## 5. 의사결정 기준

새 결정을 내릴 때는 아래 기준을 우선한다.

- 코어 CRM 흐름을 단순하게 만드는가
- 멀티테넌시와 감사 추적을 해치지 않는가
- 로컬 실행이 필요한 문제를 서버로 억지 이동시키지 않는가
- 외부 AI와의 연결 가능성을 열어두는가
- 초기 제품 범위를 과도하게 넓히지 않는가
