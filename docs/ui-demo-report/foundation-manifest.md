# Foundation 화면 이미지 매니페스트

Estate ERP의 인증·홈·업무·매물 기반 화면 13개를 같은 운영 시스템으로 정리한 구현용 매니페스트다. 모든 이미지는 2026-07-17 기준 실제 한국 중개 업무 데이터와 상태를 넣은 1440×900 동비율 데스크톱 시안이며, built-in ImageGen으로 생성한 뒤 `view_image`로 잘림·중복 패널·주요 텍스트 가독성을 확인했다.

## 공통 시각 시스템

- 기준 이미지: `assets/reference/master-estate-operational-system.png`
- 앱 셸: 인증·온보딩을 제외하고 216px 사이드바 + 48px 글로벌 헤더
- 색: `#F7F6F3` 배경, `#FFFFFF` 표면, `#2F2D2A` 본문, `#3F63D8` 활성/주요 행동
- 밀도: 14px 한국어 본문, 40px 데이터 행과 입력, 8px 간격 배수, 1px 경계선
- 형태: 6px radius, 그림자 최소화, 색상과 상태 텍스트를 항상 함께 제공
- 금지: 대형 카드·과도한 공백·그라디언트·글래스·파스텔 장식·소비자 포털 스타일·외부 제품 로고 복제
- 구현 기준: Tailwind v4 + shadcn/ui로 재현할 수 있는 표, 탭, split pane, inspector, sticky action bar 조합

## 01. 로그인

- **Route:** `/login`
- **제목:** 로그인
- **Recipe:** Product proof + authentication form
- **이미지:** `assets/screens/foundation/01-login.png`
- **1차 목적:** 대표자·직원이 자신의 사무소 업무 공간에 안전하게 진입한다.
- **반드시 보이는 요소:** Estate ERP 식별자, 로그인 ID/비밀번호, 로그인 유지, 비밀번호 찾기, 주 로그인 버튼, 사무소 코드 로그인, 계정 개설 진입, 좌측 실제 매물 데이터 증거.
- **참고 제품:** Attio workspace shell의 절제된 컨트롤 밀도.
- **채택한 구조:** 52:48 분할. 왼쪽은 세 기능 증거와 4행 매물 표, 오른쪽은 400px 로그인 폼이다. 제품 가치와 입력 작업을 한 화면에서 분리한다.
- **대안 A:** 단일 중앙 폼 + 하단 보안/기능 증거 스트립. 작은 노트북에는 유리하지만 제품 맥락 전달이 약하다.
- **대안 B:** 사무소 코드 우선 화면 → 사용자 로그인 2단계. 다중 사무소 사용에는 명확하지만 최초 로그인 시간이 늘어난다.
- **구현 유의점:** 직원 ID(`GD7291-0001`)와 대표 이메일을 동일 필드에서 허용하고, 비밀번호 오류·잠금·인증 만료 상태를 폼 높이 변화 없이 표시한다.

## 02. 회원가입

- **Route:** `/register`
- **제목:** 대표자 계정 만들기
- **Recipe:** Progress rail + verified owner form + trust summary
- **이미지:** `assets/screens/foundation/02-register.png`
- **1차 목적:** 사무소를 개설할 대표자 계정과 이메일 인증을 완료한다.
- **반드시 보이는 요소:** 3단계 진행, 이름·휴대전화·이메일, 인증번호와 제한 시간, 비밀번호 요구사항, 필수/선택 동의, 취소/계속, 데이터 격리·권한·감사 기록 안내.
- **참고 제품:** Attio의 간결한 폼 컨트롤과 상태 표현.
- **채택한 구조:** 230px 진행 레일 + 640px 폼 + 260px 신뢰 패널. 계정 생성과 서비스 안전 근거를 나란히 둔다.
- **대안 A:** 이메일 인증을 별도 전체 화면으로 분리. 집중도는 높지만 단계 왕복이 늘어난다.
- **대안 B:** 우측 슬라이드 패널 회원가입. 기존 앱 맥락을 유지하지만 신규 사용자가 제품 셸을 먼저 이해해야 한다.
- **구현 유의점:** 인증번호 재전송/만료, 이메일 중복, 비밀번호 조건을 서버 검증 결과와 일치시키고 입력값을 온보딩 단계까지 보존한다.

## 03. 사무소 온보딩

- **Route:** `/onboarding/office`
- **제목:** 사무소 정보 등록
- **Recipe:** Setup wizard + operational preview
- **이미지:** `assets/screens/foundation/03-onboarding-office.png`
- **1차 목적:** 법적 사무소 정보와 초기 운영 기본값을 검증해 멀티테넌트 공간을 개설한다.
- **반드시 보이는 요소:** 2/3 단계, 사무소명·대표자·등록번호, 법정 주소 검색, 연락처, 직원 수, 주요 업무, 가격/면적 단위, 생성될 사무소 코드, 권한 미리보기, 개설 버튼.
- **참고 제품:** Notion database layout builder의 설정/미리보기 분리.
- **채택한 구조:** 왼쪽 진행 레일, 중앙 검증 폼, 오른쪽 개설 미리보기. 입력 결과가 코드·권한에 어떻게 반영되는지 즉시 보여준다.
- **대안 A:** 주소와 등록번호를 먼저 검색해 사무소 정보를 자동 채우는 lookup-first 흐름.
- **대안 B:** 채팅형 단계별 안내. 초보자에게 친절하지만 전체 입력 상태를 한눈에 보기 어렵다.
- **구현 유의점:** 중개사무소 등록번호와 주소는 서버에서 중복 확인하고, 사무소 코드는 생성 후 바뀌지 않는다는 점을 제출 전에 명시한다.

## 04. 대시보드

- **Route:** `/dashboard`
- **제목:** 오늘의 업무 현황
- **Recipe:** Exception-first operational dashboard
- **이미지:** `assets/screens/foundation/04-dashboard.png`
- **1차 목적:** 사장님과 직원이 오늘 처리할 위험·후속 업무·일정·거래 흐름을 우선순위대로 파악한다.
- **반드시 보이는 요소:** 검증/후속/광고/수수료 KPI, 우선 처리 큐, 오늘 일정, 거래 파이프라인, 광고·검증 위험, 팀 업무량, AI 발견 변화와 검토 행동.
- **참고 제품:** Attio reports의 모듈 조합, Notion dashboard global filter의 공통 필터.
- **채택한 구조:** KPI 1행 + 좌우 52:48 운영 영역 + 하단 AI 인사이트 레일. 차트보다 업무 목록과 기한을 우선한다.
- **대안 A:** 역할별 개인 피드 중심 홈. 직원에게 유리하지만 사장님의 전체 운영 판단이 약해진다.
- **대안 B:** 지도 중심 관제 홈. 현장 방문과 지역 밀도에는 강하지만 계약·정산 위험이 뒤로 밀린다.
- **구현 유의점:** KPI는 클릭 시 동일 필터가 적용된 목록으로 이동하고, 사용자 역할에 따라 수수료·팀 성과 노출 권한을 제한한다.

## 05. AI 검토함

- **Route:** `/inbox`
- **제목:** AI 검토함
- **Recipe:** Triage queue + field diff + approval inspector
- **이미지:** `assets/screens/foundation/05-inbox.png`
- **1차 목적:** AI·규칙 엔진·MCP가 제안한 변경을 근거와 영향 범위를 확인한 뒤 승인하거나 거절한다.
- **반드시 보이는 요소:** 대기/승인/거절 탭, 위험도 있는 제안 큐, 현재값/제안값 diff, 근거 3종, 신뢰도, 영향 요약, 검토자/사유, 승인·거절·재확인, 감사 정보와 적용 미리보기.
- **참고 제품:** Linear inbox의 선택/처리 상태, Attio notifications의 연대기.
- **채택한 구조:** 340px 큐 + 560px 제안 상세 + 360px 결정 패널의 3-pane. 판단 근거와 실제 쓰기 행동을 물리적으로 분리한다.
- **대안 A:** 제안 하나를 전체 화면 record page로 열기. 복잡한 변경에는 좋지만 연속 검토 속도가 떨어진다.
- **대안 B:** 표 기반 일괄 승인. 저위험 제안에는 빠르지만 고위험 가격·계약 변경에 부적합하다.
- **구현 유의점:** 승인 직전 서버에서 원본 버전을 재검증하고 충돌 시 diff를 갱신한다. `ActivityLog.actor/source`와 변경 전후 값을 원자적으로 기록한다.

## 06. AI 채팅 + 결과 캔버스

- **Route:** `/ai-chat`
- **제목:** AI 도우미
- **Recipe:** Conversation + inspectable result canvas
- **이미지:** `assets/screens/foundation/06-ai-chat.png`
- **1차 목적:** 자연어로 CRM을 조회·분석하고, 구조화된 결과와 쓰기 제안을 검토함으로 보낸다.
- **반드시 보이는 요소:** 최근 대화, CRM 연결/승인 필요 권한, 사용자 질문, 도구 실행 기록, 인용 데이터 수, 제안 업무, 결과 표, 선택 항목 상세, 출처/근거/실행 기록 탭, 검토함 전송.
- **참고 제품:** Attio Ask의 calm prompt, Notion Agent의 작업 공간 위 docked assistant.
- **채택한 구조:** 42% 대화 + 58% 영속 결과 캔버스. 답변 텍스트와 실제 데이터 조작 후보를 분리한다.
- **대안 A:** 채팅 안에 표와 카드 모두 삽입. 단순 질의에는 빠르지만 긴 결과의 재탐색성이 낮다.
- **대안 B:** 명령 팔레트형 AI. 단축 실행에는 강하지만 복합 분석의 맥락 축적이 어렵다.
- **구현 유의점:** 읽기 결과와 쓰기 제안을 시각/권한 수준에서 구분하고, 쓰기 도구는 항상 `/inbox` 승인 객체를 생성하도록 한다.

## 07. 업무

- **Route:** `/tasks`
- **제목:** 업무 관리
- **Recipe:** Grouped task ledger + record inspector
- **이미지:** `assets/screens/foundation/07-tasks.png`
- **1차 목적:** 지연·오늘·예정 업무를 기록 맥락과 함께 빠르게 처리한다.
- **반드시 보이는 요소:** 내 업무/팀/지연/완료 보기, 완료 진행률, 그룹 목록, 연결 매물, 담당자·기한·우선순위·출처, 선택 업무 상세, 체크리스트, 활동 이력, 완료/기한 변경.
- **참고 제품:** Attio tasks의 낮은 마찰 행, Linear custom views의 저장된 필터/상태 문법.
- **채택한 구조:** 그룹형 ledger + 420px inspector. 목록을 떠나지 않고 전화·기록·체크리스트를 처리한다.
- **대안 A:** 단계별 kanban. 흐름 시각화는 좋지만 하루 기한 순 실행에 불리하다.
- **대안 B:** 캘린더/타임블록 중심. 일정 업무에는 강하지만 미정 기한과 대량 큐 관리가 약하다.
- **구현 유의점:** 완료·기한 변경은 낙관적 업데이트 후 실패 시 복구하고, 시스템/AI 생성 업무는 `TaskSource`를 텍스트로 노출한다.

## 08. 캘린더

- **Route:** `/calendar`
- **제목:** 업무 캘린더
- **Recipe:** Week grid + linked event inspector + deadline lane
- **이미지:** `assets/screens/foundation/08-calendar.png`
- **1차 목적:** 상담·현장 방문·계약 일정과 광고/입금 마감을 시간 축에서 함께 조율한다.
- **반드시 보이는 요소:** 월/주/일/일정 전환, 날짜 탐색, 직원/유형 필터, 종일 마감, 08–19시 주간 그리드, 현재 시간, 겹친 일정, 선택 일정의 참여자·연결 거래·체크리스트·문서, 하단 마감 업무.
- **참고 제품:** Attio activity timeline의 연결 맥락, Twenty calendar의 데이터 기반 캘린더.
- **채택한 구조:** 실제 주간 시간 그리드 + 340px inspector + 하단 deadline lane. 이벤트와 마감 업무를 구분하되 같은 화면에서 본다.
- **대안 A:** 월간 밀도 뷰 + 우측 하루 agenda. 장기 조망에는 좋지만 시간 충돌 확인이 약하다.
- **대안 B:** 직원별 열을 가진 day scheduler. 팀 배차에는 좋지만 주간 거래 흐름이 사라진다.
- **구현 유의점:** 시간대·종일 이벤트·반복·드래그 변경을 지원하고 계약금/중도금/잔금은 계약 스케줄에서 파생된 읽기 전용 원본 링크를 유지한다.

## 09. 매물 목록

- **Route:** `/properties`
- **제목:** 전체 매물
- **Recipe:** Saved-view operational grid + compact property inspector
- **이미지:** `assets/screens/foundation/09-properties.png`
- **1차 목적:** 대량 매물을 검증·광고·연락·다음 행동 기준으로 검색하고 일괄 처리한다.
- **반드시 보이는 요소:** 저장 보기, 명시적 필터 문법, 표/지도/동호수 전환, 밀도/열 설정, 선택 개수와 bulk action, 13행 매물 데이터, 열 계산, 사진/관계/위치/활동/광고가 있는 inspector.
- **참고 제품:** Attio table의 열/계산/선택 정밀도, Attio record overview의 highlights/relationships.
- **채택한 구조:** frozen-column 표 + 우측 360px inspector. 기준 master와 달리 저장 보기·bulk action·열 합계를 전면화했다.
- **대안 A:** 50:50 목록+지도. 지역 탐색에는 좋지만 열 비교와 일괄 작업 폭이 줄어든다.
- **대안 B:** 단지→동→호수 계층 브라우저. 아파트 재고에는 강하지만 단독/토지와 교차단지 검색이 약하다.
- **구현 유의점:** TanStack Table 가상화, 열 고정/폭 저장, URL filter state, 키보드 탐색을 적용한다. 금액은 만원 저장값을 억/만원으로 일관되게 포맷한다.

- **참고 제품:** Attio record overview와 activity timeline.
- **채택한 구조:** 340px identity panel + 유연한 record canvas. 좌측 불변 식별정보와 우측 업무 맥락을 분리한다.
- **대안 A:** 전체 폭 문서형 상세 + 우측 floating actions. 읽기에는 좋지만 반복 속성 탐색이 느리다.
- **대안 B:** 탭마다 완전히 독립된 전체 화면. 기능별 집중은 좋지만 핵심 상태가 탭 사이에서 끊긴다.
- **구현 유의점:** Property/Site/Dong/Unit/Contact/Deal의 관계를 페이지 단위 병렬 로딩하고, 가격 변경은 반드시 `PriceHistory`와 감사 로그를 함께 생성한다.

## 11. 매물 등록

- **Route:** `/properties/new`
- **제목:** 매물 등록
- **Recipe:** Five-step wizard + sticky validation summary
- **이미지:** `assets/screens/foundation/11-property-new.png`

- **구현 유의점:** 단계별 draft를 서버에 저장하고, 외부 광고는 소유자·권리·필수 사진 검증이 모두 완료될 때만 활성화한다. m²와 평은 단일 m² 원본에서 계산한다.

## 12. 외부 매물 수집

- **Route:** `/properties/external-listings`
- **제목:** 외부 매물 수집
- **Recipe:** Import triage + aligned field comparison + merge decision
- **이미지:** `assets/screens/foundation/12-external-listings.png`
- **1차 목적:** 외부 채널에서 수집한 매물을 기존 CRM과 비교해 중복·신규·제외를 안전하게 결정한다.
- **반드시 보이는 요소:** 수집 상태/마지막 동기화, 대기/중복/가져옴/제외 탭, source/confidence 큐, 외부 vs CRM 필드 비교, 사진 비교, 판단 근거와 인용, 병합 필드 선택, 반영 영향, 병합 승인/소유자 확인 업무.
- **참고 제품:** Linear inbox의 triage, Attio AI confidence의 신뢰도·근거·인용.
- **채택한 구조:** 420px 수집 큐 + 590px 비교 + 320px 결정 inspector. 발견·비교·쓰기 결정을 분리한다.
- **대안 A:** 표에서 행 단위 빠른 가져오기. 신규 추정 항목에는 빠르지만 중복 병합에 위험하다.
- **대안 B:** 외부 원문과 CRM 상세를 50:50 전체 화면 비교. 근거 확인은 쉽지만 큐 처리량이 감소한다.
- **구현 유의점:** 수집 원문 snapshot과 canonical URL을 보존하고, 병합은 필드별 allowlist·낙관적 버전 확인·감사 로그를 적용한다. 외부 값으로 소유자 연락처를 자동 덮어쓰지 않는다.

- **Route:** `/properties/naver-my-ads`

- **Recipe:** Channel status grid + renewal readiness inspector
