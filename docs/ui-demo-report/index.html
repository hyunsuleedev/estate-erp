Direction study

비교한 세 방향

1번을 공통 셸로 채택하고 2번의 문서·상세 문법, 3번의 지도·공간 문법을 필요한 화면에만 결합했다.

1. Operational Grid

매일 쓰는 표, 저장 뷰, 선택 레코드, 활동과 다음 행동. 전체 시스템의 기본 골격.

2. Structured Workspace

문서, 계약 조항, 자료실, 상세 layout과 side peek에 선택적으로 사용.

3. Estate Command Center

매물 지도, 관리단지, 동·호수처럼 공간과 운영 문맥이 동시에 필요한 화면에 사용.

Shared UI system

화면이 흔들리지 않게 하는 공통 규칙

스타일을 통일하는 수준이 아니라 목록→상세→행동→감사의 전환 규칙까지 공통화한다.

색과 표면

따뜻한 중성색을 유지하되 canvas, surface, selected, warning의 명도 차이를 현재보다 크게 한다.

밀도와 가독성

사이드바 216px, 헤더 48px, 목록행 40px, 입력 36px, 본문 14px. 1440×900에서 15–18행을 목표로 한다.

목록과 상세

DataIndex는 저장 뷰→filter→table/map/board→quick peek 순서를 고정한다. 복잡한 편집은 URL을 가진 full page로 승격한다.

안전과 감사

법적·금전·AI 변경은 대상, before/after, 영향, actor/source, 승인, undo를 표시한다. 색이나 drag만으로 확정하지 않는다.

Implementation roadmap

구현은 화면 수가 아니라 recipe 순서로

39개 route를 각각 따로 만들면 다시 일관성이 무너진다. 공통 토큰과 세 핵심 recipe를 먼저 만든 뒤 전문 작업면을 얹는다.

P0 · 공통 기반

먼저 디자인 시스템을 코드로 고정

현재 Desktop/Web에 흩어진 스타일을 공유 계층으로 모으고 고밀도 데이터 작업면의 기준을 만든다.

  • semantic color·density·type token
  • AppShell·DataIndex·RecordWorkspace
  • Money·Area·Address·Status·Relation cell
  • virtualized table·saved view·quick peek
P1 · 일상 코어

가장 많이 왕복하는 흐름부터

매물과 고객을 연결한 뒤 업무·캘린더·단지·매칭·거래가 같은 record/activity 문법을 쓰게 한다.

  • 매물 목록·상세·등록·광고
  • 연락처·구매조건·상담·통화
  • 업무·캘린더·AI 검토함
  • UnitMatrix·Match·Deal pipeline
P2 · 전문 작업면

법적·금전·협업 위험을 별도 설계

범용 CRM 패턴으로 처리하면 안 되는 영역을 전문 recipe와 감사 규칙으로 완성한다.

  • 계약 문서·지급 timeline
  • 캐시플로우·원장·파트너/직원 정산
  • 중개 네트워크·자료·사진
  • 설정·권한·MCP·AI 운영
