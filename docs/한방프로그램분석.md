## 2. 메인 네비게이션 (7개 탭)

`app/krenmain_hsty.ini`의 최근 작업 히스토리에서 드러난 **한방 메인 IA**:

```
고객 / 내매물 / 정보망매물 / 파발방 / 파발마검색 / 일정 / 계약
```

### Estate ERP 사이드바 레퍼런스
- **"정보망매물"**(다른 사무소가 공유한 매물)이 내매물과 별도의 **1급 탭**. 중개사 일상 사용량을 반영한 배치.
- 현재 Estate ERP는 Network를 하위에 숨겨둠 → 탑레벨 탭 승격 검토.
- "파발방"(공유 내보내기)과 "파발마검색"(요청 수신)을 분리 탭으로 둠.

### 히스토리 파일이 노출한 실사용 예시
```ini
[내매물]
Caption=상업용건물 월세 남현동 $빌라 매매 대치동 12-1$아파트 매매 삼천동1가 585-10 ...
[정보망매물]
Caption=상업용건물 월세 서울특별시 강남구 청담동$...$지식산업센터 매매 서울특별시 강동구 고덕동
```

### 컬럼 세트의 **4차원 키 시스템**

`GRID_MY` 섹션 키 포맷: **`{거래구분}_{매물종류그룹}_{매물종류}`**

```
0_00_00=...   # 전체 × 전체 × 전체 (기본)
1_00_00=...   # 매매 × 전체
1_02_00=...   # 매매 × 분양권군 (아파트분양권/주상복합분양권)
1_06_00=...   # 매매 × 단독/다가구/상가주택군
2_06_00=...   # 전세 × 단독/다가구군
3_06_00=...   # 월세 × 단독/다가구군
```

- 첫 자리(거래구분): `0`=전체 / `1`=매매 / `2`=전세 / `3`=월세 / `4`=**연세** / `5`=매매+임대 / `6`=임대+임대
- 둘째(매물종류군): `00`=전체, `01`=아파트/주상복합, `02`=분양권, `03`=오피스텔, `04`=오피스텔분양권, `05`=연립/빌라/다세대, `06`=단독/다가구/상가주택, `07`=펜션/전원주택, `08`=원룸, `09`=상가/사무실, `10`=상업용건물, `11`=숙박, `12`=공장/아파트형공장/창고, `13`=토지, `14`=재개발
- 셋째(세부코드): 01=아파트, 02=아파트분양권, 03=주상복합, 04=주상복합분양권, 05=오피스텔, 06=오피스텔분양권, 07=연립, 08=빌라, 09=다세대, 10=단독, 11=다가구, 12=상가주택, 13=원룸, 14=상가점포, 15=상업용건물, 16=사무실, 18=토지, 19=재개발, 20=숙박, 21=펜션, 22=전원주택, 23=공장, 24=아파트형공장, 25=창고

### Estate ERP UI에 주는 힌트
매물 타입 필터가 바뀌면 **표시 컬럼 세트가 자동 교체**되어야 한다. 한방이 이미 4차원 조합으로 이 UX를 구현해 두었다. `Listing` 리스트 페이지의 컬럼 세트를 **거래구분 × 매물종류 조합별 프리셋**으로 저장하는 설계가 업계 표준.

### Estate ERP 설계안
현재 `NetworkInquiry`는 "매물에 대한 문의"만 커버. **"이런 매물 구합니다"(Buy Request)는 없음**.

**추가할 엔티티**:
```prisma
model NetworkBuyRequest {
  id            String @id
  officeId      String
  roomId        String       // FK → NetworkRoom
  createdById   String       // FK → User (요청 올린 직원)
  transactionType String     // sale/jeonse/monthly/yearly_rent
  siteTypes     String[]
  regions       String[]     // 희망 지역 (시/구/동 code)
  priceMin      Int?
  priceMax      Int?
  depositMin    Int?
  depositMax    Int?
  monthlyRentMax Int?
  title         String
  content       String       // "급매 찾습니다, 판교 30평대..."
  status        String       // active / matched / closed / expired
  expiresAt     DateTime?
  createdAt     DateTime
}

model NetworkBuyRequestResponse {
  id                  String @id
  buyRequestId        String // FK
  responderOfficeId   String
  responderUserId     String
  listingId           String?  // 매칭 제안할 매물 (NetworkSharedProperty로 공유된 것)
  message             String
  status              String   // pending / accepted / rejected
  createdAt           DateTime
}
```

원 `BuyerRequirement`와 **뷰만 겹치고 데이터 소스는 분리**:
- `BuyerRequirement`: 내 사무소 내부 구매 고객 관리 (private)
- `NetworkBuyRequest`: 중개방에 공개된 구매 요청 (public to room)
- 사장님이 `BuyerRequirement` → "이걸 네트워크에 올리기" 버튼으로 `NetworkBuyRequest` 생성
