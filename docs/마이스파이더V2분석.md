# 마이스파이더 V2 프로그램 분석

> `/Users/hyunsulee/estate-sample/Assetmaker/MySpiderII.exe`를 .NET 디컴파일해 Estate ERP 설계에 참고할 수 있는 업무 흐름, 화면 모듈, 데이터 필드, 차별화 포인트를 정리한 문서.

## 1. 요약

샘플은 `MySpider V2` 계열의 Windows 설치형 중개사무소 ERP다. C# WinForms + DevExpress 기반이고, 서버와는 `WebAgentController.do` 단일 JSON 트랜잭션 게이트웨이로 통신한다. 로컬에는 주소록, 통화, 문자, 일정 캐시용 SQLite DB가 있으며 KT/LGU+/삼성 070 CTI DLL, DevExpress Report, Excel/인쇄/계약서 모듈이 함께 배포되어 있다.

Estate ERP 관점에서 참고 가치가 높은 부분은 다음이다.

- `내물건`과 `공개물건`을 분리한 매물 운영 UX
- 물건별 소유자/임차인 상담을 매물 저장 흐름 안에 묶는 구조
- 고객 알림/매칭 기능이 단순 추천이 아니라 상담/쪽지/공개물건 탐색과 연결되는 구조
- 공동주택 동/호수 배치표와 입주고객 관리
- 통화 수신 팝업에서 고객/상담/물건/최근통화 이력을 한 번에 보여주는 구조
- 계약서/확인설명서/거래신고/영수증/표지 등 문서 자동화 범위

주요 네임스페이스와 역할:

| 네임스페이스 | 역할 |

| `MySpiderMgr.OpenEsta` | 공개물건 검색, 다른 사무소 물건 확인 요청, 중개사 정보 |

| `MySpiderMgr.CustAlert` | 공개 손님/내 손님 알림, 매물-고객 매칭, 알림 메모 |
| `MySpiderMgr.DocuMngt` | 계약/문서/거래신고/특약/공유 |

| `MySpiderMgr.MineCall` | 통화 내역, 녹취, 수신/발신/부재중 필터 |
| `MySpiderMgr.NoteMngt` | 사무소 간 쪽지, 그룹, 대화형 조회 |
| `MySpiderMgr.Billboard` | 대시보드 위젯, 오늘/다음 일정, 만기/거래신고 알림, 공지 |

서버 통신은 `APClient`가 담당한다. 모든 요청은 `HEADER`와 `REQ_DATA`를 가진 JSON으로 묶이고, 응답은 `HEADER`와 `RTN_DATA`로 온다. 그리드 데이터는 `GRID_0`, `GRID_1` 형태의 `COL`/`ROW` 배열로 전달된다. 서비스 ID는 `MEDS001Q01`, `CMLS001I01`, `DMSV001Q01`처럼 화면/도메인/CRUD 성격이 섞인 코드로 구분한다.

## 4. 로컬 캐시 DB

`KPA_API.dat`는 주소록 캐시다.

주요 테이블:

- `address_data`: 고객/회사/연락처 기본정보
- `address_phone`: 전화번호 다건 관리
- `address_group`: 주소록 그룹
- `address_link`: 그룹-주소록 연결
- `network_group`: 네트워크/그룹 구조
- `sync_info`: 테이블별 동기화 시각

`KPD_API.dat`는 전화/문자/일정 캐시다.

주요 테이블:

- `call_list`: 통화 목록
- `call_list_opt`: 통화 부가 상태
- `call_reco`: 녹취 파일 메타데이터
- `call_memo`: 통화 메모
- `sms_list`, `mms_data`: 문자/MMS 이력
- `schedule`: 알림 일정
- `todo_data`: 화면 메모/할 일
- `mem_tel`, `svc_tel`, `svc_mobile`: 전화 서비스 설정
- `address_ref`: 연락처 참조

Estate ERP는 이미 `CallRecording`, `Consultation`, `CalendarEvent`가 있으나, CTI Phase에서 `CallLog` 성격의 별도 모델이 필요하다. 녹음 파일이 없거나 아직 업로드되지 않은 전화 이벤트도 남겨야 하기 때문이다.

## 5. 매물 관리 UX

`Layout010*.xml`과 `MEDS001Q1P.cs` 기준 내물건 목록/상세의 핵심 컬럼:

- 관심, 소개, 공개, 상태
- 거래구분
- 물건종류 대/중/소분류
- 지역, 상세주소, 간략위치
- 물건명, 동, 호, 층, 탑층, 방, 욕실, 향
- 공급/전용/대지/연면적/지분
- 매매가, 전세가, 월보증금, 월세, 융자금, 현임차, 권리금, 평단가, 인수가
- 간략소개, 한줄메모, 옵션사항기타
- 등록일, 수정일, 수정자
- 소유자명/연락처/상담일/상담내역
- 임차인명/연락처/상담일/상담내역
- 만기일, 확인요청

특징:

- 한 물건 입력 화면 안에서 소유자 고객과 임차인 고객을 같이 편집한다.
- 거래구분에 따라 금액 입력 필드를 동적으로 바꾼다.
- 건물 종류에 따라 면적 라벨과 필드를 바꾼다.
- 공개 여부, 관심 여부, 추천 여부, 소개 여부를 별도 플래그로 둔다.
- 공개된 물건의 등록일 자동변경 기능이 있다.
- 사진은 공개/비공개 플래그를 개별로 둔다.

Estate ERP 반영 포인트:

- 광고/공개 상태는 Listing 플래그로 중복 저장하지 않고 `ListingAdvertisement`에서 관리한다.
- `Listing.memo` 하나로는 부족하다. `shortDescription`, `internalMemo`, `optionMemo`, `ownerLastConsultation`, `tenantLastConsultation`처럼 화면에 반복 노출되는 메모의 용도가 분리되어야 한다.
- `PropertyContact`와 `Tenant`는 설계가 좋다. 다만 목록 성능을 위해 마지막 소유자/세입자 상담 요약은 조회 전용 projection 또는 materialized view가 필요하다.

## 6. 고객/희망조건

고객 목록 레이아웃은 일반 고객, 물건 연결 고객, 구하는 고객을 나눠 보여준다.

주요 필드:

- 관심 고객 여부
- 고객 대/소분류
- 고객 그룹
- 고객명
- 연락처1, 연락처2
- 상담내역, 최종상담일
- 한줄메모
- 희망 지역 최대 3개
- 희망 물건명/종류
- 희망 면적 범위
- 희망 매매/전세/월세 금액 범위
- 진행상태, 완료/보류 여부

Estate ERP 반영 포인트:

- `BuyerRequirementRegion`이 이미 이 구조를 잘 받는다.
- `BuyerRequirementSite`도 필요하다. 샘플은 지역 기반이 강하지만, 현대 UX에서는 단지 지정이 더 중요하다.
- `Contact.phone`, `phone2`만으로는 CTI와 기존 업무 관성에 부족할 수 있다. `ContactPhone` 다건 모델 또는 JSONB 보조 전화 목록을 검토할 만하다.
- 고객 분류는 단순 태그가 아니라 업무 흐름을 바꾼다. 예: 구하는 고객, 내놓는 고객, 입주고객, 기타 고객.

## 7. 고객 알림/매칭

`CustAlert` 모듈은 공개 손님/내 손님 알림과 매물 매칭을 다룬다. 매칭 조건은 지역, 면적, 금액, 물건명 포함 여부로 세분화된다. 알림에서 바로 매물 확인, 상담 메모, 사무소 쪽지/전화/문자로 이어진다.

Estate ERP 반영 포인트:

- `Match`는 이미 파이프라인 중심으로 잘 설계되어 있다.
- 추가로 “고객 알림 feed”가 필요하다. 이것은 `Match`와 다르다. `Match`는 내부 매칭 결과이고, 알림 feed는 네트워크/공개 고객 요청 채널이다.
- `NetworkInquiry`를 매물 문의뿐 아니라 “구하는 고객 요청”에도 대응시키려면 `NetworkBuyRequest` 또는 `NetworkRequirement` 계열 모델이 필요하다.

## 8. 공동주택 동/호수 배치표와 입주고객

`OccuMngt` 모듈은 Estate ERP의 `Site → Dong → Unit → Property` 설계와 직접 대응된다.

기능:

- 공동주택 선택 후 동 목록 조회
- 동별 호수/라인 배치표 생성
- 평형/타입/색상 일괄 지정
- 빈호수/필로티/피난안전구역 같은 셀 상태 지정
- 동/호 별칭 변경
- 소유자/임차인 입주고객 등록
- 만기일 또는 입주 예정일로 일정 생성
- 배치표 공개/다운로드 기능

Estate ERP 반영 포인트:

- `Unit`에 `isExisting`, `isPiloti`, `isSafetyArea`, `alias`, `displayColor` 같은 UI 상태 필드를 둘지 검토해야 한다.
- 현재 `Unit.lineNo`, `floor`는 좋다. 샘플처럼 “라인 전체 일괄 지정” UX가 필요하다.
- `Tenant`와 `PropertyContact` 등록은 동/호 배치표에서 바로 가능해야 한다.
- 입주고객 화면은 단순 Tenant 목록이 아니라 “호실 그리드 + 고객 상태” 화면이어야 한다.

## 9. CTI/통화/문자

샘플은 KT OpenAPI, LGU+, 삼성 070, MULTICID 계열 DLL을 포함한다. `MineCall`, `MyCall`, `PhoneInfo`, `ucPhoneHistory`가 통화 업무를 담당한다.

통화 팝업/조회 구조:

- 수신일/수신시간
- 전화번호
- 고객명
- 신규구분
- 통화상태
- 물건정보
- 고객구분
- 최종상담내역
- 고객/사무소/문서/통화이력 병렬 조회

Estate ERP 반영 포인트:

- `CallRecording`은 녹음 파일 중심이다. 수신/발신 이벤트 자체를 담는 `CallLog` 모델이 별도로 필요하다.
- `Contact`와 `VendorContact`를 통합 검색하는 `all_contacts_view` 구상은 맞다.
- 전화 팝업은 고객명만 보여주면 부족하다. 최근 상담, 연결된 매물, 구하는 조건, 미완료 업무를 같이 보여줘야 한다.
- 문자 발송 이력은 Phase 1 이후라도 `MessageLog`로 분리해 둘 가치가 있다.

## 10. 계약/문서 관리

`DocuMngt`는 가장 큰 모듈 중 하나다. 계약 입력 폼과 DevExpress Report가 다수 포함되어 있다.

문서 종류:

- 아파트/오피스텔/일반 부동산 매매·전세·월세 계약
- 분양권 계약
- 상가/권리 양도·승계
- 표준임대차 계약
- 전대차 계약
- 중개대상물 확인설명서
- 임대차 신고서
- 계약갱신 요구권 행사 여부 확인서
- 임대보증금 보증 관련 서식
- 영수증, 거래대장, 표지, 정산 관련 출력물

목록 컬럼:

- 거래신고 상태
- 공유구분
- 중개구분
- 공동중개사무소
- 계약/문서 종류
- 거래구분
- 소재지
- 금액, 계약일, 중도금일, 잔금일
- 한줄메모
- 매도/임대인, 매수/임차인 연락처

Estate ERP 반영 포인트:

- 현재 `Contract`는 법적 계약 내용 중심으로 좋다.
- `DealPayment`로 실제 돈 흐름과 계약서 명목 금액을 분리한 설계도 샘플보다 낫다.
- 추가로 `ContractDocument` 또는 `DocumentTemplate` 계층이 필요하다. 계약 한 건에 여러 출력 서식/부속 문서/거래신고 상태가 붙기 때문이다.
- 계약 공유 기능은 `Network`와 별도 권한 모델이 필요하다. 공동중개 사무소와 계약서 일부 공유는 채팅방 공유와 다르다.

## 11. 일정/대시보드

대시보드는 위젯 기반이다.

주요 위젯:

- 중개사무소 정보
- 오늘 일정
- 다음 일정
- 임대 만기도래
- 물건 확인 요청 알림
- 거래신고 예정 알림
- 공지사항
- 친목회/커뮤니티 게시판

일정은 월/주/일 보기, 상태, 색상, 팝업 알림, 공개 여부를 가진다.

Estate ERP 반영 포인트:

- `CalendarEvent`에 `status`, `color`, `popupAt`, `sourceEntityType`/`sourceEntityId`를 추가하면 샘플 UX를 더 쉽게 구현할 수 있다.
- 대시보드는 “통계”보다 “오늘 해야 할 업무/기한/알림” 중심이어야 한다.

## 12. 외부 서비스 연동

샘플은 다음 성격의 외부 연동을 가진다.

- 네이버/우리집 매물 광고 상태 확인 및 전송
- 주소 검색 팝업
- 지도/상권/인구 리포트
- SMS/MMS 서비스
- 070 전화 API
- 웹 기반 공지/도움말/결제/약관
- FTP 기반 이미지/파일 업로드

Estate ERP 반영 포인트:

- 외부 연동은 `IntegrationAccount`, `IntegrationSyncLog`, `ListingAdvertisement`로 분리하는 편이 좋다.
- 광고 상태는 `Listing` 본체가 아니라 `ListingAdvertisement`에 둔 현재 설계가 맞다.
- 지도/상권 리포트는 Phase 2에서 `Insight` 또는 `PublicDocument`와 분리된 `MarketReport`가 어울린다.

## 13. Estate ERP에 바로 반영할 설계 후보

우선순위 높음:

1. `CallLog` 모델 추가: 녹음 없는 통화 이벤트, 수신/발신/부재중, 전화번호, 연결 Contact, 연결 Property/Listing, 상담 전환 여부.
2. `ContactPhone` 다건 모델 검토: CTI 검색, 대표번호, 별칭, 암호화/마스킹, 전화번호 변경 이력 대응.
3. `ContractDocument`/`DocumentTemplate` 모델 추가: 계약서 본문과 부속 문서/출력 서식/거래신고 상태 분리.
4. `Unit` UI 상태 확장: 필로티, 피난안전구역, 빈호수, 별칭, 색상, 라인 일괄 편집.
5. 네트워크에 `NetworkBuyRequest` 추가: 구하는 고객/희망조건을 사무소 간 공유하는 채널.

우선순위 중간:

1. `CalendarEvent`에 색상/팝업/완료상태/원천 엔티티 필드 추가.
2. `Listing` 또는 `ListingAdvertisement`에 공개/소개/추천/관심 표시 상태를 세분화.
3. 고객/물건 목록의 컬럼 프리셋 저장 기능.
4. 사무소 간 쪽지형 메시지와 네트워크 룸 채팅의 관계 재정의.
5. 대시보드 위젯을 임대만기, 거래신고, 확인요청, 오늘 일정 중심으로 구성.

## 14. 현재 Estate ERP 설계와 비교

이미 잘 반영된 부분:

- `Site → Dong → Unit → Property → Listing` 분리
- `PropertyContact`와 `Tenant` 분리
- `BuyerRequirement`와 `Match` 분리
- `Deal`과 `Contract` 분리
- `ListingAdvertisement`를 별도로 둔 구조
- `ExternalListingGroup`으로 외부 매물 호실 그룹을 기억하는 구조
- `NetworkSharedProperty`, `NetworkInquiry`, `NetworkMessage`
- `CallRecording`과 `Consultation` 연결

보강이 필요한 부분:

- 통화 이벤트 모델은 녹음 모델과 분리해야 한다.
- 문서/계약 출력물 계층이 아직 부족하다.
- 네트워크는 매물 공유뿐 아니라 구하는 고객 공유까지 필요하다.
- 호실 그리드의 UI 메타데이터가 부족하다.
- 고객 연락처 다건 관리가 약하다.

## 15. 결론

마이스파이더 V2는 구식 설치형 구조지만, 실제 중개사무소 업무 흐름은 잘 드러난다. Estate ERP는 데이터 모델을 더 정돈된 형태로 이미 잡고 있으나, 샘플에서 배울 점은 “업무 진입점”이다. 중개사는 매물, 고객, 전화, 계약을 각각 따로 쓰지 않고, 전화 수신 → 고객 확인 → 매물/희망조건 확인 → 상담 기록 → 일정/계약으로 이어지는 한 화면 흐름을 기대한다.

따라서 Phase 1 이후 데스크톱 UX는 CRUD 화면을 늘리는 것보다 `Call Workspace`, `Unit Occupancy Grid`, `Document Workspace`, `Network Buy Request`를 중심으로 잡는 것이 맞다.
