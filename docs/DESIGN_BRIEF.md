# Estate ERP — 디자인팀 브리핑

> 대상: 프로덕트 디자인팀
> 작성일: 2026-04-18
> 목적: 프로젝트 전체 맥락 공유 + 디자인이 필요한 상세 페이지 요청

---

## 1. 프로젝트 한 줄 요약

**한국 부동산 중개사무소용 통합 SaaS ERP.** 매물·고객·상담·거래·일정·업체 관리 + 사무소 간 매물 공유 네트워크 + 외부 AI(Claude/ChatGPT)와 MCP로 연결되는 데이터 허브를 하나의 데스크톱 앱으로 제공합니다.

## 2. 왜 만드는가

### 현재 시장의 문제
- 매물, 고객, 상담, 거래, 일정이 **여러 도구와 카톡/엑셀/메모장에 흩어져** 있습니다.
- CTI(전화), 광고(네이버 부동산), 매물 공유(공동중개), 직원 관리가 **전부 분리된 도구**로 운영됩니다.
- 국내 경쟁 제품(중개왕·부기사)은 **웹 중심·구식 UI**로 설치형 데스크톱의 신뢰감과 로컬 연동(전화/녹음) 요구를 충족하지 못합니다.
- AI를 쓰고 싶어도 **CRM 데이터와 실제 업무 액션이 연결되지 않습니다**.

### 우리가 푸는 문제
1. 매물 → 고객 매칭 → 상담 → 계약 → 수수료 정산이 **하나의 파이프라인**으로 이어지게.
2. 사무소 간 **공동중개 네트워크**를 제품 내부에 내장 — 카톡방에서 벗어난 구조화된 매물 공유.
3. 외부 AI가 **MCP로 CRM을 직접 조작** — "이번 주 계약 만료되는 세입자에게 연락 태스크 만들어줘" 같은 명령이 바로 실행됨.

## 3. 대상 사용자

- **Primary**: 3~20명 규모의 중개법인/팀. 사장님(owner) + 실장(manager) + 소속공인중개사(agent).
- **Secondary**: 1인 중개사.
- **연령**: 40~60대가 주력. 한국어 UI 필수, 정보 밀도 높은 화면 선호, 엑셀 스타일 테이블에 익숙.

## 4. 제품 원칙 (디자인에 영향 있는 것만)

1. **데스크톱이 메인, 웹은 보조.** Electron 설치형 데스크톱 앱이 주 사용 환경. 해상도는 1440×900 이상 가정.
2. **정보 밀도 > 여백의 미학.** 한국 중개사무소 사용자는 한 화면에 많이 보이는 걸 선호합니다. SaaS 트렌드의 과도한 화이트스페이스는 지양.
3. **테이블 중심 + 상세 패널 패턴.** 좌측 목록, 우측 상세가 자연스럽습니다.
4. **모바일은 Phase 4.** 현재는 데스크톱만 집중.
5. **멀티테넌시.** 모든 화면에 "어느 사무소"인지는 최상단에 항상 고정.

## 5. 기술 스택 (디자인 환경)

- **Framework**: React 19 + TanStack Router/Query
- **Styling**: Tailwind v4 + **shadcn/ui** (이미 세팅됨)
- **Icons**: Lucide
- 디자인 결과물은 shadcn 컴포넌트 조합으로 구현 가능한 형태면 가장 좋습니다.

## 6. 핵심 데이터 구조 (디자인 이해에 필요한 만큼만)

```
Site(단지/건물) → Dong(동) → Unit(호) → Property(관리단위) → ListingIntake(의뢰)
                                                               ↓
                                                          Listing(거래 옵션)
                                                               ↓
Contact(사람) ←→ BuyerRequirement(구매희망) ──── Match ─────→ Deal → Contract
                                                               ↓
                                                        CommissionPayment (수수료 수금)
```

- **Site**: 래미안고덕 같은 아파트 단지, 빌라, 상가, 토지까지 전부 포함.
- **ListingIntake**: 의뢰 생명주기(open/hold/closed)와 확인 이력. 확인 표시는 이력에서 파생됩니다.
- **Listing**: 의뢰 안의 매매/전세/월세 가격 옵션. 거래중/완료는 연결된 Deal에서 파생됩니다.
- **Contact**: 사람 1명. 소유자든 구매자든 세입자든 한 테이블에 들어가고, 관계 테이블로 역할이 결정됩니다.
- **Deal**: 거래 진행 — 수수료 매도측/매수측 분리, 공동중개 시 상대 중개사 몫도 분리 기록.

## 7. 디자인이 필요한 상세 페이지

아래는 `docs/desktop-prd/pages/` 에 상세 PRD가 이미 작성되어 있는 페이지들입니다. 디자인팀은 각 페이지별 PRD를 읽고, 레이아웃·정보구조·인터랙션을 디자인해주시면 됩니다.

### 7.1 CRM 코어 페이지

| 페이지 | 핵심 화면 요소 | 난이도 |
|---|---|---|
| **매물 목록/상세** (listings) | 엑셀 스타일 테이블(확인상태 파이프라인 시각화) + 상세 패널(가격 변동 이력, 사진, 매물 관련인) | 🔴 상 |
| **관리 단지** (office-sites) | 즐겨찾기 단지 그리드 + 단지별 호실 매트릭스(floor × lineNo 네이버 스타일) | 🔴 상 |
| **연락처** (contacts) | 통합 연락처 목록 + 관계도(가족/법무사 연결) + 거래 이력 타임라인 | 🟡 중 |
| **구매 희망조건** (buyer-requirements) | 조건 카드 리스트 + 매칭 후보 매물 우측 패널 | 🟡 중 |
| **매칭** (matches) | 파이프라인 칸반(suggested → viewing → negotiating → closed) | 🟡 중 |
| **거래** (deals) | 거래 파이프라인 칸반 + 수수료 계산기(매도/매수/공동중개 분리) | 🔴 상 |
| **계약** (contracts) | 계약금/중도금/잔금 타임라인 + 입금 확인 체크리스트 | 🟡 중 |
| **태스크** (tasks) | 리스트 + 필터(담당자/상태/마감일) + 간단한 캘린더 뷰 | 🟢 하 |
| **캘린더** (calendar) | 월/주/일 뷰 + 잔금일·수금일·계약일 색상 구분 | 🟡 중 |

### 7.2 차별화 기능 페이지

| 페이지 | 핵심 화면 요소 | 난이도 |
|---|---|---|
| **공동중개 네트워크** (network) | 중개방(카톡방 메타포) 리스트 + 방 내부(공유 매물 피드 + 채팅) + 매물 공개범위 마스킹 설정 UI | 🔴 상 |
| **AI 챗** (ai-chat) | 챗 UI + 도구 호출 결과 카드(매물/연락처 inline 표시) | 🟡 중 |
| **직원 관리** (employees) | 직원별 실적 카드 + 수수료 정산 현황 + 급여 유형(고정/혼합/수수료제) | 🟡 중 |
| **통화 작업 공간** (call-workspace) | 통화 팝업 + 상담 기록 폼 + 녹음 업로드 (Phase 2 구현, 디자인은 먼저) | 🟡 중 |

### 7.3 수수료/캐시플로우 (별도 설계 필요)

현재 PRD 파일은 없지만 **사장님이 가장 많이 보게 될 화면**입니다. 3가지 뷰가 필요합니다.
- **타임라인 뷰**: 월별 시간순 수금 예정/완료
- **칸반 뷰**: pending → collected / overdue / partial / waived
- **리스트 뷰**: 테이블 + 필터
- **수금 캘린더**: 잔금일·수금일 월별 달력
- **순이익 카드**: 수금 완료 − 고정비 = 이번달 순이익

### 7.4 업체 디렉토리 (별도 설계 필요)

거래 후 하자 발생 시 업체를 찾는 화면. 카테고리(배관/도배/청소…) + 지역 필터 + 업체 카드(여러 담당자 번호).

## 8. 공통으로 필요한 디자인 시스템 요소

1. **앱 셸**: 좌측 사이드바(네비) + 상단 바(사무소 스위처 + 검색 + 알림 + 사용자) + 본문.
2. **파이프라인 시각화 컴포넌트**: Listing 확인상태·Match·Deal·Contract 모두 단계별 상태가 있습니다. 일관된 비주얼이 필요.
3. **사람 카드 / 매물 카드 / 거래 카드**: 목록·상세·매칭·공유 등 여러 곳에서 반복 사용됩니다.
4. **금액 표기 규칙**: 만원 단위 저장 → "15억 8,000" 같이 한국식 표기로 렌더링. 디자인 토큰으로 통일 필요.
5. **주소 표기**: 시도·시군구·읍면동 + 도로명/지번. 축약 표기 규칙.
6. **상태 뱃지**: 확인상태·거래단계·수금상태 등 상태가 많습니다. 컬러 시스템 정리 필요.
7. **빈 상태(Empty state)**: 매물 0개, 매칭 0개 등 — 다음 액션으로 유도하는 일러스트/카피.

## 9. 디자인팀에 요청하는 것

1. **페이지별 상세 PRD**(`docs/desktop-prd/pages/*.md`)를 읽고, 각 페이지의 **와이어프레임 → 하이파이** 순서로 진행해주세요.
2. 디자인 시스템 요소(8번 항목)를 먼저 정리해주시면 이후 페이지 작업이 빨라집니다.
3. 경쟁 제품(중개왕, 부기사, 공인중개사협회 한방) UI를 한 번 훑고 **우리가 무엇을 다르게 할지** 관점을 잡아주세요. 특히 정보 밀도와 현대적 UI 사이 균형.
4. **Figma 파일 구조**: 페이지 단위로 파일 분리하지 말고, 한 파일 안에 섹션(프레임)으로 구분해주세요. 개발이 한 번에 훑기 편합니다.
5. 불확실한 업무 맥락(예: "공동중개 수수료 배분이 실제로 어떻게 이뤄지나") 은 언제든 물어봐주세요. 도메인 이해가 가장 중요합니다.
