# 계약서 작성 기능 분석 및 구현 기준

기준일: 2026-07-13

## 결론

estate-erp의 계약 기능은 `문서 종류를 골라 범용 문자열을 저장하는 화면`에서
`거래 데이터 자동 채움 → 계약서별 구조화 입력 → 법정 필수사항 검증 → 초안 검토 →
출력본 고정` 흐름으로 전환해야 한다.

첫 번째 완결 단위는 **주거용 부동산 매매계약서**다. 매매계약서의 입력·검증·출력
경계를 먼저 확정한 뒤 같은 문서 코어 위에 주택 임대차계약서와 주거용 중개대상물
확인·설명서를 순서대로 추가한다.

## 마이스파이더에서 확인한 범위

### 공개 자료로 확인되는 사실

AssetMaker의 MySpider V2 모바일 동반 앱 `APSpider2` 공개 설명에서 다음 범위가
확인된다.

- PC 프로그램과 모바일 앱이 연동된다.
- 고객 상담 내역과 계약 진행상태를 조회한다.
- 계약일·중도금일·잔금일 등 계약 일정을 관리한다.
- 알림, 메시지, 사진 등 현장 업무 데이터를 모바일에서 확인한다.

공개된 화면이나 매뉴얼만으로는 계약서의 실제 입력 필드, 상태 코드, PDF 생성 방식,
전자서명 방식을 확정할 수 없다. 따라서 아래 내부 구조 참고값을 마이스파이더의
현재 공식 사양으로 표현하면 안 된다.

공개 근거: [APSpider2 Google Play](https://play.google.com/store/apps/details?id=com.asset.apspider2)

### 저장소에 남아 있는 역분석 참고값

기존 조사 문서에는 `DocuMngt` 계열에서 관찰한 다음 패턴이 기록돼 있다.

- 계약 마스터: `DMSV001I01`
- 계약 문서 상세 공통 패턴: `DMSV003I01`, `DMSV003Q01`
- 중개대상물 확인·설명서: `DMSV002I01`, `DMSV002Q01`
- 사무소 재사용 출력 양식: `DMSV005I01`, `DMSV005Q01`
- 계약 당사자: `TPCT02S`
- 추가 당사자·대리인·공동명의: `TPCT28S`
- 부동산 목록: `TPCT27S`

이를 통해 얻을 수 있는 제품 설계상의 핵심은 다음과 같다.

1. 계약 마스터와 실제 출력 문서를 분리한다.
2. 문서 종류별 상세 입력을 분리한다.
3. 공동명의·대리인·법인 담당자를 반복 가능한 당사자로 관리한다.
4. 사무소 문구와 출력 양식을 계약별 데이터와 분리해 재사용한다.
5. 계약일·중도금일·잔금일은 계약 데이터에서 일정으로 파생한다.

서비스명과 테이블명을 그대로 복제하지 않고 위 경계만 estate-erp 도메인에 맞게
적용한다.

## 현행 코드의 문제

기존 구현에는 문서 템플릿 30종과 마이스파이더 입력폼·리포트 클래스명 매핑이 이미
들어 있다. 그러나 실제 동작은 모든 문서를 같은 범용 필드와 같은 A4 요약표로
처리하는 프로토타입이다.

- `ContractDocument.metadata`의 문자열 필드만 저장한다.
- 매매계약서·임대차계약서·확인설명서가 같은 입력 구조를 쓴다.
- 연락처 전화번호와 중개사무소 정보가 계약 응답에 충분히 포함되지 않는다.
- 매도인/매수인이 각각 한 명뿐이며 공동명의·대리인·법인을 표현할 수 없다.
- 대금 합계, 필수 날짜, 인도·소유권 이전, 확인설명서 교부일 검증이 없다.
- `window.print()`만 있고 서버에 렌더 파일, 해시, 개정 이력이 남지 않는다.
- MCP 계약 도구는 조회만 가능해 AI가 안전한 초안 작성에 참여할 수 없다.

## 법적 기준

### 거래계약서

일반 부동산 매매·임대차 거래계약서에는 하나의 강제 서식이 있는 것이 아니라
공인중개사법 시행령 제22조의 필수 기재사항이 적용된다.

- 거래당사자의 인적사항
- 물건의 표시
- 계약일
- 거래금액·계약금액과 지급일
- 물건 인도일
- 권리이전의 내용
- 계약 조건 또는 기한
- 중개대상물 확인·설명서 교부일
- 그 밖의 약정 내용

개업공인중개사의 서명·날인이 필요하고, 실제 중개한 소속공인중개사가 있으면 함께
서명·날인해야 한다. 거래계약서는 5년 보존 대상이다.

- [공인중개사법 시행령 제22조 연계정보](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lspttninfSeq=106767)
- [공인중개사 서명·날인 관련 연계정보](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1010875017)

### 중개대상물 확인·설명서

확인·설명서는 법정 서식을 사용하며 3년 보존하고 거래당사자에게 교부해야 한다.

- 별지 제20호: 주거용 건축물
- 별지 제20호의2: 비주거용 건축물
- 별지 제20호의3: 토지
- 별지 제20호의4: 입목·광업재단·공장재단

2026-02-15부터 확인 근거자료에 신탁원부와 건축물대장 등본이 법문상 명시됐다.

- [공인중개사법 시행규칙 현행 서식](https://law.go.kr/lsInfoP.do?lsiSeq=263573)
- [주거용 확인·설명서 PDF](https://www.law.go.kr/LSW/flDownload.do?bylClsCd=110202&flSeq=141860969&gubun=)
- [2026 확인 근거자료 개정 연계정보](https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=1000269343)

### 주택임대차 표준계약서

서면 주택임대차계약에는 법무부·국토교통부가 마련한 표준계약서를 우선 사용한다.
현재 게시된 한국어 원본은 2023-10-06 개정본이며 2026-03-10에는 영어·중국어·
베트남어 번역본이 추가됐다.

- [법무부 주택임대차표준계약서](https://www.moj.go.kr/moj/314/subview.do)
- [2023-10-06 원본 PDF](https://www.moj.go.kr/sites/moj/download/20231006_01.pdf)

### 신고와 전자계약

- 매매 신고 기준일은 계약서에 임의로 적은 날짜가 아니라 중요사항의 실제 합의일이다.
- 신고 대상 매매는 실제 계약 체결일부터 30일 이내 신고한다.
- 대상 주택 임대차는 보증금 6천만원 초과 또는 월세 30만원 초과 시 체결일부터
  30일 이내 신고한다.
- 국토교통부 IRTS는 당사자 본인확인·전자서명, 공인중개사 공동인증서 서명,
  실거래·임대차·확정일자 자동 신청, 공인전자문서센터 보관을 제공한다.

estate-erp 자체의 문서 작성과 IRTS 수준의 전자계약은 같은 기능이 아니다. 전자서명,
본인확인, 공인전자문서 보관, 신고 자동 신청은 공식 시스템 또는 인증 사업자와의
연동 범위로 둔다.

- [IRTS 전자계약 절차](https://irts.molit.go.kr/usr/cmn/main/home/RtecsHelp.do)
- [IRTS 프로그램 개요](https://irts.molit.go.kr/usr/cmn/main/home/RtecsInfo.do)

## 적용 아키텍처

### 1차: 주거용 매매계약서

`ContractDocument.metadata.contractAgreement`에 다음 버전 스키마를 저장한다.

- `schemaId`, `schemaVersion`
- 실제 계약 체결일, 문서 작성일
- 도로명·지번 주소, 동·층·호 등 대상 표시
- 토지 지목·면적, 건물 구조·용도·면적
- 총 매매대금, 계약금·중도금·잔금과 각 지급일
- 인도일, 소유권 이전일, 권리관계 정리 내용
- 조건·기한, 확인·설명서 교부일, 특약
- 반복 가능한 매도인·매수인 스냅샷
- 중개사무소·개업공인중개사·소속공인중개사 표시

서버와 웹이 같은 공유 스키마와 검증 함수를 사용한다. 초안은 필드가 부족해도 저장할
수 있지만 `generated`, `signed`, `submitted` 상태로 진행하려면 오류가 없어야 한다.

### 개인정보 원칙

주민등록번호나 법인등록번호 원문은 일반 JSONB와 활동 로그에 저장하지 않는다. 첫
구현은 마스킹된 식별정보와 신분 확인 여부만 다룬다. 원문 식별번호가 필요한 단계에서는
별도 암호화 컬럼, 키 관리, 복호화 권한, 열람 감사 로그, 출력 후 마스킹 정책을 먼저
구현해야 한다.

### MCP 원칙

AI 도구는 바로 계약을 확정하거나 서명 상태로 바꾸지 않는다.

- `prepare_sale_contract_draft`: CRM의 거래·매물·연락처·사무소 데이터를 읽어
  구조화된 매매계약서 **초안**을 만들거나 보완한다.
- `validate_sale_contract_draft`: 필수기재사항 누락, 대금 불일치, 공적장부 재확인
  항목을 읽기 전용으로 검사한다.

사용자가 화면에서 검토하고 출력본을 고정하는 승인 경계를 유지한다.

## 후속 구현 순서

1. 주거용 매매계약서 전용 입력·검증·미리보기
2. 계약 출력본 서버 렌더링, PDF/R2 저장, SHA-256 해시와 개정 이력
3. 반복 당사자를 `ContractParty` 정규 테이블로 승격
4. 복수 중도금·기타 지급을 `ContractPaymentSchedule`로 승격하고 CalendarEvent 파생
5. 주거용 중개대상물 확인·설명서와 공적장부 스냅샷
6. 주택임대차 표준계약서와 임대차 신고
7. 매매 신고 사건(`FilingCase`)과 신고필증 상태 관리
8. IRTS 또는 인증 사업자 연동 검토

`계약일·중도금일·잔금일 알림`은 규칙 엔진이 아니라 계약 데이터에서 일정을 생성하는
스케줄러/이벤트 핸들러 책임으로 구현한다.
