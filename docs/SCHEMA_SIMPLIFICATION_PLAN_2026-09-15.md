# 의뢰 중심 스키마 단순화 분석

검토일: 2026-09-15. 대상: `/Users/hyunsulee/estate-erp` 현재 체크아웃.

이 문서는 현재 소스에서 확인한 사실과 재설계 제안을 구분한다. 운영 DB의 데이터 분포나 적용된 마이그레이션을 조회하지 않았으며, 구현·마이그레이션은 수행하지 않았다. 이전 전체 검토는 [스키마 적합성 분석](SCHEMA_FIT_REVIEW_2026-09-14.md)을 참고한다.

## 1. 권장 결정

**공급·수요 의뢰를 독립적인 업무 단위로 만들고, BrokerageCase를 선택적 업무 묶음으로 축소한다. 고객원장의 표시 묶음은 조회 결과로 만든다.**

이번 개편에서 ListingIntake와 BuyerIntake를 통합 테이블로 합치지는 않는다. Property, Listing, BuyerRequirement, Match, Deal, Contract의 기존 ID와 업무 의미를 유지한다.

성공 기준은 테이블 개수 감소보다 다음 세 가지다.

1. 새 의뢰를 만들 때 다른 의뢰나 업무철을 자동으로 찾아 합칠 필요가 없다.
2. 의뢰의 당사자·주 연락처 변경이 다른 관계 테이블의 참여자 병합을 요구하지 않는다.
3. 고객원장의 정렬·묶음 방식을 바꿔도 저장된 의뢰의 소속·정체성이 바뀌지 않는다.

## 2. 현재 복잡성의 원인

### 같은 고객을 근거로 두 단계에서 자동 연결한다

- `BuyerRequirementsService.create()`는 buyerIntakeId 없이 contactId로 호출되면, createNewIntake가 켜져 있지 않은 경우 그 고객의 가장 최근 열린 의뢰를 재사용한다.
- 새 의뢰가 생성되는 경우 `resolveBrokerageCaseForIntake()`가 실제 당사자 집합이 같은 활성 업무철을 찾아 붙인다.
- 따라서 “실거주용 새집을 찾는 김씨”에게 “투자용 오피스텔 조건”을 추가할 때, 의뢰와 업무철 양쪽에서 의도하지 않은 병합이 가능하다.

근거: [구매조건 생성](../apps/server/src/modules/buyer-requirements/buyer-requirements.service.ts), [업무철 자동 연결](../apps/server/src/modules/brokerage-cases/brokerage-case.resolver.ts).

### 고객원장의 표시 단위가 저장 구조를 지배한다

- 데스크톱 `/customers`, `/customers-table`은 `api.brokerageCases.ledger()`를 사용한다.
- 행 식별·펼치기·선택과 대표 고객 표시가 BrokerageCase에 의존한다.
- 서버 원장은 참여자가 없는 업무철을 제외한다. 고객 미확인 공급 의뢰는 매물 원장에는 남지만 고객원장에는 표시되지 않는다.
- 두 의뢰의 brokerageCaseId는 필수다. 단순 접수도 업무철을 생성해야 한다.

근거: [원장 서비스](../apps/server/src/modules/brokerage-cases/brokerage-cases.service.ts), [원장 응답 타입](../packages/api-client/src/modules/brokerage-cases.ts), [고객원장](../apps/desktop/src/renderer/routes/_authenticated/customers/index.tsx), [표 원장](../apps/desktop/src/renderer/routes/_authenticated/customers-table/index.tsx).

### 사람 관계를 복사한 뒤 병합해서 유지한다

- 구매 의뢰에는 BuyerIntakeContact가 있지만 공급 의뢰에는 대응하는 참여자 모델이 없다.
- 공급 측은 PropertyContact를 읽어 업무철 참여자로 복사한다.
- 구매 의뢰 참여자의 추가·역할 변경은 업무철 참여자 병합을 호출한다. 제거 경로에는 이에 대응하는 업무철 참여자 제거가 없다.
- 업무철 병합은 기존 role과 principal/primary 값을 누적하는 방식이다. 의뢰의 대표 연락처를 바꿔도 이미 지정된 케이스 대표가 자동으로 같은 사람으로 바뀌는 구조가 아니다.

이 동작은 공유 업무철의 다른 의뢰 정보를 지우지 않으려는 방어지만, 현재 관계와 과거 참여 이력이 한 명부에 함께 남는 결과를 만든다.

근거: [구매 의뢰 참여자 변경](../apps/server/src/modules/buyer-intakes/buyer-intakes.service.ts), [관련인 변경](../apps/server/src/modules/property-contacts/property-contacts.service.ts), [참여자 병합](../apps/server/src/modules/brokerage-cases/brokerage-case.resolver.ts).

## 3. 대안 비교

| 대안 | 장점 | 한계 | 판단 |
|---|---|---|---|
| 현 구조 유지, 검증만 강화 | 변경 범위가 작음 | 필수 업무철·중복 명부·자동 연결 문제 유지 | 단기 오류 수정에만 적합 |
| 의뢰 독립, 업무철 선택, 원장 조회 분리 | 기존 매물·거래 ID 유지, 불필요한 동기화 제거 | 원장 API와 두 화면의 데이터 연결 전환 필요 | **권장** |
| 공급·수요를 공통 Intake로 통합 | 공통 담당자·상담·참여자 FK를 통일 가능 | 유형별 자식 모델, 잘못된 유형 연결 방지, 여러 FK·API 이관 필요 | 공통 기능 중복이 실제 유지비의 중심이 된 뒤 재평가 |
| Case를 완전히 제거하고 의뢰끼리만 연결 | 한 계층 제거 | 갈아타기 제목·메모·여러 의뢰 묶음의 소유자가 사라짐 | 현재 Dependency 모델과 기록의 사용량 확인 전에는 권하지 않음 |

공통 Intake는 잘못된 설계가 아니다. 다만 현재 공급 의뢰는 특정 Property, 유효성 확인, 방문·권리 메모를 갖고 수요 의뢰는 복수 희망조건을 갖는다. 공통 필드 몇 개를 없애기 위해 새로운 공통 부모 계층을 만들면 이번에 줄이려는 계층 수가 다시 늘어날 수 있다.

## 4. 목표 모델과 정보의 소유자

| 정보 | 유일한 편집 원본 | 다른 화면에서 사용법 |
|---|---|---|
| 사람의 이름·현재 전화번호 | Contact / ContactPhone | 관계에서 참조 |
| 부동산 소유·관리 관계 | PropertyContact | 의뢰 참여자의 후보로 제시 |
| 이번 공급 의뢰 참여자 | **ListingIntakeContact — 신규 제안** | 고객/업무철 화면에서 조회 |
| 이번 수요 의뢰 참여자 | BuyerIntakeContact | 고객/업무철 화면에서 조회 |
| 의뢰 책임자 | 각 Intake의 assignedToId — 신규 제안 | 원장·업무 화면에서 조회 |
| 의뢰의 접수·보류·종결 | 각 Intake | 고객별 상태는 의뢰들의 집계로 표시 |
| 매매·전세·월세 대안 | Listing | 매칭·광고가 참조 |
| 원하는 집의 대안 조건 | BuyerRequirement | 매칭이 참조 |
| 관련 의뢰의 명시적 묶음 | BrokerageCase | 필요한 업무철에서만 표시 |
| 고객원장의 한 묶음 | 저장하지 않는 응답 객체 | 화면 전용 키로 구분 |
| 계약 체결 당시 당사자 표기 | ContractParty / 문서 Revision | Contact의 현재 정보와 구분 |

### 공급 의뢰 참여자

`ListingIntakeContact`의 최소 필드 제안:

```text
id, officeId, listingIntakeId, contactId
roles          # principal / requester / representative / viewing_contact / other 등 검증된 값
isPrimary      # 이번 의뢰의 주 연락창구
createdAt, updatedAt
```

- roles 배열은 같은 사람이 당사자이자 의뢰인인 경우처럼 중복 역할을 허용하기 위한 것이다. 허용값·중복 제거는 검증한다.
- principal은 이번 의뢰의 당사자다. 부동산의 소유 지분은 PropertyContact에서 관리한다.
- 연락창구는 의뢰별로 최대 한 명이다. 별도 primaryContactId를 같이 저장하지 않는다.
- 동일 의뢰·Contact 조합은 한 행으로 제한하고, officeId를 포함한 FK로 동일 사무소를 강제한다.
- 최초 문의는 Consultation/CallLog 같은 접수 근거로 남긴다. 현재 주 연락처를 최초 문의자로 간주하지 않는다.
- 현재 구매 의뢰는 연락처 한 명 이상 규칙을 유지한다. 공급 의뢰는 고객 미확인 수입 데이터를 허용하고 “의뢰인 미확인”으로 다룬다.
- PropertyContact는 참여자 후보를 제시하는 데 사용할 수 있지만 의뢰 생성 뒤 자동 동기화하지 않는다. 자동 수입에서 후보를 임시 기록한다면 추정 출처를 보존하고 확인된 의뢰인으로 표시하지 않는다.
- 처음부터 범용 역할·관계·기간 테이블을 연속해서 추가할 필요는 없다. 현재 참여자 변경의 전후 이력을 남기고, 종결 의뢰 수정은 이유를 기록하는 명시적 정정으로 제한한다. 과거 명칭·전화번호까지 고정하는 문서 스냅샷과는 구분한다.

### 업무철

- `BrokerageCase` 이름과 테이블은 우선 유지한다. 제목·공동 목적 메모·보관 상태와 연결 의뢰를 소유한다.
- ListingIntake.brokerageCaseId, BuyerIntake.brokerageCaseId는 최종적으로 선택 값으로 바꾼다. 일반 의뢰의 기본값은 null이다.
- 한 의뢰는 업무철 0개 또는 1개에 소속한다. 여러 업무철 동시 소속은 현재 요구 근거가 없어 도입하지 않는다.
- 업무철의 사람 목록은 하위 의뢰 참여자를 중복 제거해 조회한다. 역할은 어느 의뢰에서의 역할인지 함께 전달한다.
- 케이스 전체 주 연락처를 의뢰 전체의 대표로 전파하지 않는다. 실제 “갈아타기 전체 연락창구” 요구가 생길 때 별도로 정의한다.
- `BrokerageCaseParticipant`는 신규 원본 역할을 중단하고, 기존 메모·고유 참여정보가 보존된 뒤에만 폐기한다. 관련 정보가 남아 있으면 읽기 전용 과거 기록으로 보존한다.
- `casePriorityRank`는 업무철 내부 순서에만 사용한다. 의뢰의 중요도·고객 정렬 순서로 재사용하지 않는다.
- 케이스 보관은 묶음 보관이며 하위 의뢰를 자동 종결시키지 않는다.

### 업무철 의존관계

기존 `BrokerageCaseDependency`는 유지한다. 매도대금·일정 의존은 실제 업무 의미가 있으며 단순화 대상이 아니다.

의존관계가 있는 의뢰를 케이스에서 분리할 때는 일반 소속 변경을 거부한다. 관계를 명시적으로 처리하거나 관련 의뢰·의존관계를 한 트랜잭션에서 옮기는 전용 명령이 필요하다. 기존 복합 FK를 “변경이 불편하다”는 이유로 제거해서는 안 된다.

nullable 케이스 FK는 기본 FK 규칙에서 null일 때 검사를 건너뛸 수 있으므로, 의뢰 자체의 officeId FK와 참여자·Dependency의 동일 사무소 제약을 독립적으로 유지해야 한다. [PostgreSQL FK 공식 문서](https://www.postgresql.org/docs/16/ddl-constraints.html#DDL-CONSTRAINTS-FK)

## 5. 의뢰를 나누는 기준부터 명확히 한다

**하나의 목표를 달성하기 위한 대안은 같은 의뢰, 각각 따로 성사되어야 하는 목표는 다른 의뢰**로 정한다.

| 상황 | 저장 결과 |
|---|---|
| 한 집을 매매 또는 전세로 내놓음 | Property 1, ListingIntake 1, Listing 2 |
| 한 채 살 집을 A단지 또는 B단지에서 찾음 | BuyerIntake 1, 하나의 조건에 선호단지 2개 또는 서로 다른 조건 2개 |
| A단지와 B단지에서 각각 한 채씩 구매 | BuyerIntake 2 |
| 기존 집을 팔아 새집을 구매 | 공급 의뢰 1 + 수요 의뢰 1 + 명시적 Case·Dependency |
| 같은 고객이 별도로 투자용 상가도 구함 | 별도 BuyerIntake, 기존 Case에 자동 합류하지 않음 |
| 매도 의뢰 취소 뒤 나중에 다시 의뢰 | 과거 의뢰를 보존하고 새 접수 회차 생성. 단순 실수 정정/복원은 기존 의뢰 |
| 소유자와 의뢰인·방문 연락처가 다름 | PropertyContact와 의뢰 참여자의 역할을 구분 |

기존 “Property당 닫히지 않은 공급 의뢰 하나”는 현재 아파트 중개 범위에서 유지한다. 같은 집에 독립된 이해관계자의 복수 활성 의뢰까지 지원하려면 거래 배타성·권한을 다시 설계해야 하므로 이번 단순화에서 풀지 않는다.

## 6. API와 원장 표시를 함께 바꾼다

### 쓰기 명령

- **새 의뢰 접수**: 참여자와 조건을 받아 새 Intake를 만든다. 요청 재시도 방지는 요청 키로 처리하며 사람 집합을 중복 키로 삼지 않는다.
- **기존 의뢰에 조건 추가**: buyerIntakeId를 명시한다. contactId만 보고 가장 최근 의뢰를 선택하지 않는다.
- **관련 의뢰 묶기/분리**: caseId와 정확한 Intake ID를 명시하는 별도 명령으로 처리한다.
- **연락처 수정**: 연락처만 변경한다. 의뢰 관계 변경은 의뢰 API에서 수행한다.

화면은 현재 선택된 의뢰 ID를 자동으로 명령에 넣을 수 있다. 사용자가 매번 ID나 업무철을 선택하게 할 필요는 없다. 사용자에게 보이지 않는 임의 추정과, 현재 명확한 선택 문맥을 사용하는 것은 구분한다.

### 읽기 응답

새 고객원장 API는 Case 모델 반환 대신 다음 의미의 응답을 제공한다. 예시는 설계 초안이며 아직 존재하지 않는 API다.

```text
CustomerLedgerGroup
  groupKey                 # 화면용 키. caseId나 contactId로 쓰기 요청하지 않음
  primaryContact           # 표시용 연락창구
  participants             # 표시 중인 의뢰에서 유도
  intakes[]
    kind + id              # listing / buyer, 실제 쓰기 대상
    participants
    assignedTo
    lifecycleStatus
    options[]              # Listing 또는 BuyerRequirement
    brokerageCase          # 선택적 업무철 요약
    latestConsultation     # 이 의뢰에 연결된 상담
```

- 기존 “고객 아래 내놓음·구함을 펼치는” 표시를 유지할 수 있다. 고객별 묶음은 같은 의뢰라는 뜻이 아니다.
- 기본 묶음은 의뢰의 주 연락창구 기준으로 구성하고, 한 의뢰는 한 번만 노출한다. 공동 참여자 이름 검색도 해당 의뢰를 찾되 복제하지 않는다.
- 연락창구 미확인 공급 의뢰도 조회 대상에서 누락하지 않는다. 고객원장 내 미확인 묶음 또는 의뢰 목록에서 분명히 접근 가능하게 한다.
- 개인 연락처 상세에서는 참여한 모든 의뢰를 볼 수 있다. 참여자별 상세에서 같은 의뢰가 보이는 것은 정상이지만 전체 건수는 distinct Intake 기준으로 센다.
- 일반 고객상담은 Contact 문맥에 남기고, 특정 의뢰 상담만 해당 의뢰의 최근 상담으로 집계한다. 두 의뢰를 함께 다룬 상담이 필요하면 명시적 복수 연결을 별도 요구로 다룬다.
- 고객의 매도·매수별 책임자·가격·상태는 각 의뢰 행에서 표시한다. 표시 그룹에 임의의 단일 상태·담당자를 저장하지 않는다.
- 커서·정렬·선택·펼침 저장 키와 React Query 무효화 키도 새로운 그룹/의뢰 의미에 맞춰 바꾼다. 이름만 바꾼 Case DTO를 계속 반환하면 결합이 남는다.

## 8. 데이터 이관과 구현 순서

### 0단계: 실제 데이터의 이관 가능성을 읽기 전용으로 조사

케이스별 의뢰 수·종류·상태, Dependency 수, title/memo, 케이스만의 참여자·메모, 의뢰와 불일치한 대표 연락처, 고객 미확인 공급 의뢰를 센다. 현재 DB의 제약·마이그레이션 적용 상태도 확인한다.

현재 스키마는 케이스가 자동 생성됐는지 사람이 의도적으로 묶었는지를 별도로 저장하지 않는다. **의뢰 두 개가 있다는 사실만으로 갈아타기라고 해석하거나, 단일 의뢰 케이스라고 무조건 삭제하면 안 된다.**

### 1단계: 공급 참여자와 원장 조회를 추가

- 기존 테이블·관계를 유지하면서 새 참여자 모델과 새 원장 API를 추가한다.
- 구매 의뢰 참여자는 기존 BuyerIntakeContact를 그대로 사용한다.
- 과거 공급 의뢰인은 현재 PropertyContact만으로 확정 복원하지 않는다. 상담·이력·과거 스냅샷의 증거를 확인하고, 불명확한 건은 현재 관련인 후보 및 기존 케이스 기록과 함께 미확인으로 보존한다.
- 공급 의뢰에 케이스의 모든 참여자를 일괄 복사하면 구매측 사람까지 매도 의뢰인으로 잘못 옮길 수 있다.
- 이관은 출처와 처리 결과를 기록하고 반복 실행해도 중복이 생기지 않게 한다. 불확실한 행은 무조건 확정하는 대신 검토 대상으로 분리한다.

### 2단계: 클라이언트와 쓰기 경로 전환

- nullable case 및 원장 새 응답을 이해하는 서버·클라이언트를 먼저 배포 가능 상태로 만든다.
- 새 구매조건은 정확한 의뢰 ID에 추가하거나 명시적으로 새 의뢰를 만든다.
- 같은 사람이라는 이유로 기존 의뢰·케이스를 선택하는 경로를 모두 전환한다.
- Electron 구버전이 실제로 사용되는 동안 새 응답만 강제하면 안 된다. 지원 버전 전환 또는 구버전 API의 제한된 호환 계층이 필요하다.

### 3단계: 일반 의뢰의 케이스 필수성을 제거

- DB nullable 변경과 함께 Dependency 복합 FK·고유키 및 사무소 제약을 검증한다.
- 신규 일반 의뢰는 caseId=null로 생성한다. 호환용 단일 의뢰 케이스를 잠시 생성했다면 종료 조건을 두고 최종 구조에 남기지 않는다.
- 의도적으로 만든 묶음은 유지한다. 기존 자동 묶음을 한꺼번에 해체하지 않는다.
- 업무철 아카이브와 의뢰 종결을 별개로 처리한다.

### 4단계: 중복 상태와 레거시 경로 정리

- 신규 코드의 CaseParticipant 쓰기와 각 merge 호출을 제거한다.
- 케이스만의 참여자·메모·과거 연결은 보존 계획을 완료한 뒤 기존 모델을 읽기 전용화하거나 제거한다.
- 원장 Case 의존 API와 기존 contactId 자동 연결 API는 모든 호출자 전환을 확인한 뒤 폐기한다.
- 같은 단계에서 `BuyerRequirement.assignedToId`를 의뢰 책임자 체계로 옮긴다면, 조건별 담당자가 서로 다른 기존 의뢰는 임의로 한 명을 고르지 않는다. 책임자 확인 또는 실제 독립 업무인지 검토한다.

이는 새 구조 추가 → 데이터 이관 → 읽기/쓰기 전환 → 구 구조 제거 순서다. Prisma도 데이터 이관에 expand-and-contract 접근을 안내한다. 프로젝트의 Prisma 6 버전에 맞춰 실제 SQL과 이관 스크립트를 작성해야 한다. [Prisma 6 데이터 이관 문서](https://docs.prisma.io/docs/orm/v6/prisma-migrate/workflows/data-migration)

**되돌리기 한계**: 새 구조에 쓰기가 시작되기 전에는 새 읽기 경로를 끄는 것으로 되돌릴 수 있다. caseId=null 의뢰와 새 참여자가 저장된 뒤에는 이전 서버 바이너리로 단순 복귀하면 안 된다. 과도기 읽기 호환을 유지하거나 새 데이터를 보존하는 보정 이관이 필요하다. legacy 테이블을 남겨두는 것만으로 완전한 롤백이 보장되지는 않는다.

## 9. 첫 구현 범위와 완료 기준

첫 구현은 **“업무철 없이 의뢰를 접수하고 고객원장에서 관리할 수 있다”**까지로 제한한다. 새 공통 Intake, 재무 재설계, 자산 유형 확장, 계약 문서 개편을 동시에 진행하지 않는다. 사무소 격리 공백은 별도 우선 수정으로 진행하되 새 관계에도 동일 사무소 제약을 적용한다.

완료 기준:

1. 같은 고객의 독립된 두 수요 의뢰가 각각 생성되고, 조건 추가가 정확한 의뢰만 변경한다.
2. 공급 의뢰의 소유자·의뢰인·주 연락처·방문 연락처를 구분할 수 있다.
3. 대표 연락처 변경·참여자 제거가 해당 의뢰 조회에 반영되며 과거 업무철 명부에 의해 덮이지 않는다.
4. Case 없는 의뢰와 연락처 미확인 공급 의뢰가 누락되지 않는다.
5. 고객 묶음의 표시 변경이 의뢰 소속·상태·담당자를 바꾸지 않는다.
6. 명시적으로 묶은 갈아타기와 Dependency는 유지되고, 제약을 어기는 분리는 거부된다.
7. 타 사무소 Contact·Case·Intake ID로 연결할 수 없고, 동시 참여자 변경에서도 대표 연락처가 중복되지 않는다.
8. 기존 Match·Deal·Contract·광고 참조와 이관 전후 의뢰·거래 수가 보존된다.
9. 데스크톱의 실제 Electron에서 두 원장의 생성·편집·검색·선택·재열기 흐름을 검증한다.

이번 분석에서는 소스·스키마·마이그레이션 및 소비자 경로만 재확인했다. 기존 테스트 결과를 새 설계의 검증으로 재사용하지 않았으며, 새 설계를 구현하거나 DB에 적용하지 않았다.
