# Estate ERP Product Strategy

이 문서는 시장 포지셔닝, 경쟁 분석, AI/MCP 전략을 다룬다. 제품 범위는 [prd.md](./prd.md)를 기준으로 본다.

## 1. 시장 포지셔닝

Estate ERP는 한국 부동산 중개사무소를 위한 운영 시스템이다. 단순 CRM이 아니라 다음을 함께 제공하는 것이 목표다.

- 매물/고객/상담/거래를 연결하는 CRM
- 팀 단위 운영 ERP
- 공동 중개 네트워크
- MCP 기반 외부 AI 연동 지점

핵심 포지셔닝은 **“업무 시스템 + 네트워크 + AI 연결 계층”**이다.

---

## 2. 사업 모델

SaaS 구독형을 전제로 한다.

| 플랜 | 대상 | 포지션 |
|------|------|------|
| 기본 | 1인 중개사 | 기본 CRM |
| 프로 | 팀/법인 | 직원 관리, 자동화, 분석 |
| 프리미엄 | 대형 법인 | MCP, CTI, 고급 기능 |

수익화의 핵심은 단순 좌석 과금보다, 다음 기능군을 프리미엄 가치로 묶는 것이다.

- 공동 중개 네트워크
- CTI
- MCP 연결
- 고급 분석/감사 추적

---

## 3. 핵심 차별화 포인트

### 3.1 공동 중개 네트워크

국내 경쟁 제품은 개별 사무소 내부 관리에 집중하는 경우가 많다. Estate ERP는 사무소 간 공유 매물 네트워크를 제품 본체에 넣는다.

기대 효과:

- 공유 매물 풀이 커질수록 제품 가치 상승
- 단순 CRM보다 높은 락인
- 팀 내부 툴을 넘어 지역 네트워크 툴로 확장 가능

### 3.2 MCP 기반 AI 연결

CRM이 외부 AI에서 직접 조작 가능한 도구 집합이 되면, 사용자는 이미 쓰는 AI를 그대로 업무에 연결할 수 있다.

장점:

- AI 모델 비용을 제품이 직접 안아가지 않아도 됨
- 모델 교체/업그레이드에 유연함
- “AI 챗봇”이 아니라 “업무 실행 가능한 CRM”이 됨

### 3.3 설치형 메인 제품

Electron은 단순 취향이 아니라 전략이다.

- 한국 시장에서 설치형 프로그램의 신뢰감
- 로컬 연동과 상주 실행 필요
- CTI / 내장 Codex 실행 / 알림 / 트레이 기능 지원

## 4. 경쟁 환경

### 4.1 국내 경쟁

- 다방 Pro
- 직방 Pro
- 한방

공통적으로 기본 CRM/매물 관리 수요는 커버하지만, 아래는 아직 강하지 않다.

- MCP 기반 AI 연동
- 사무소 간 네트워크 공유
- 외부 AI가 직접 조작하는 CRM 인터페이스

### 4.2 글로벌 참고

글로벌 SaaS와 부동산 플랫폼은 AI 에이전트를 핵심 전략으로 채택하고 있다.

- Salesforce: 멀티 에이전트 오케스트레이션
- HubSpot: 하이브리드 인간-AI 팀
- Compass: 부동산 현장 밀착형 AI + 고객 대시보드
- Zillow: AI 기반 검색/추천/요약
- Attio: AI-native CRM + MCP 네이티브 친화 구조

Estate ERP는 이 흐름을 “한국 부동산 도메인에 맞는 현실적 버전”으로 적용한다.

## 5. AI / MCP 전략

### 5.1 왜 MCP인가

2026년 기준 MCP는 주요 SaaS와 AI 도구를 잇는 표준 연결 방식으로 자리 잡고 있다. Estate ERP가 이 생태계의 일부가 되면, 자체 AI를 키우지 않아도 외부 AI 활용성이 높아진다.

### 5.2 Estate ERP의 선택

- 제품 내부에 독자 AI를 넣지 않는다.
- CRM 서버를 MCP 친화적으로 설계한다.
- CP 브라우저 자동화와 계정 설정은 Electron과 독립된 Skills로 분리한다.
- 승인/감사 추적을 기본 설계에 포함한다.

### 5.3 단계별 적용

**Phase 1**

- CRM 데이터 읽기/쓰기 MCP 도구
- ActivityLog로 감사 추적
- 규칙 엔진 기반 알림

**Phase 2**

- UI에서 MCP 활용 흐름 노출
- AI 운영 화면 초안

**Phase 3+**

- 네이버/K-apt enrichment
- 웹훅/자동화 확장
- 승인 기반 AI 액션

## 6. 경쟁사에서 가져올 것

### Salesforce / HubSpot에서 참고할 것

- 감사 가능한 AI 실행 기록
- 승인 가능한 자동화
- 업무 시스템과 에이전트 레이어의 분리

### Compass / Zillow에서 참고할 것

- 부동산 도메인 특화 UX
- 고객 상태/진행상황 가시화
- 통화/상담/추천 흐름을 한 축으로 묶는 방식

### Attio에서 참고할 것

- MCP 도구 설계 방식
- AI가 읽고 쓰기 쉬운 데이터 모델과 인터페이스
- 통화/노트/태스크/레코드가 연결된 운영 모델

### Twenty / Frappe CRM에서 참고할 것

- 멀티테넌시 패턴
- 감사 추적
- 권한 모델
- 저장형 뷰/업무 자동화 확장 패턴

## 7. Estate ERP에 적용할 전략적 패턴

### 7.1 감사 추적을 기본 기능으로 둔다

AI를 붙이든 안 붙이든, 누가 어떤 데이터를 바꿨는지가 남아야 한다. 따라서 ActivityLog는 부가 기능이 아니라 기본 기능이다.

### 7.2 네트워크 공유를 제품 외곽이 아니라 코어 흐름에 둔다

공동 중개는 한국 부동산 업무에서 실제로 반복되는 행동이다. 별도 커뮤니티 제품으로 떼지 말고 CRM 안에서 자연스럽게 연결하는 편이 강하다.

### 7.3 고객용 대시보드는 나중에 붙일 수 있어야 한다

초기에는 내부 운영이 우선이지만, 장기적으로는 매수자/매도자에게 진행상태를 공유하는 읽기 전용 포털이 가치가 있다.

### 7.4 자동 enrichment는 로컬 + MCP 조합으로 간다

외부 스크래핑/연동은 서버에서 무리하게 돌리지 않고, 로컬 MCP를 거쳐 서버의 canonical data를 보강하는 구조가 현실적이다.

## 8. 주요 리스크

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 네이버 등 외부 연동 차단 | 높음 | 로컬 실행, 소스 다변화 |
| CTI 벤더 종속 | 중간 | Bridge 추상화 |
| 개발 범위 과대 | 높음 | Phase 단위 강한 컷 |
| 데이터 품질 부족 | 높음 | 정규화 주소, Listing 중심 모델, 감사 추적 |
| 단순 CRM으로 인식될 위험 | 높음 | 네트워크 + MCP 차별화 강조 |

---

## 9. 지금 하지 않을 것

- 제품 내 독자 AI 에이전트 플랫폼
- 복잡한 노코드 자동화 빌더
- 범용 App SDK / 마켓플레이스
- 고객 메시지 완전 자동 발송
- 승인 없는 거래 상태 변경 자동화

이들은 나중에 수익성과 운영 안정성이 확인된 뒤 확장한다.
