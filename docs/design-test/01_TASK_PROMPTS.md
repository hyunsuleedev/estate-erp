# 화면별 과제 프롬프트 (모델 비교용)

> **사용법**: 각 과제는 `[00_CONTEXT_BRIEF.md 전체] + [아래 과제 1개]`를 하나의 프롬프트로 모델에게 던진다.
> 모든 모델·모든 회차에 **토씨 하나 안 바꾸고 동일하게** 입력해야 비교가 성립한다.
>
> **통제 원칙**:
> - *무엇을* 그릴지(화면·필수 요소·상태)는 못 박는다 → 모델 A는 목록, 모델 B는 상세를 그리는 사고를 막음.
> - *어떻게* 그릴지(색·레이아웃·컴포넌트)는 절대 지시하지 않는다 → 그게 테스트 대상.
> - 출력 형식은 통일한다(아래 "공통 출력 지시") → 결과물 형태가 달라 비교 불가한 상황 방지.

## 공통 출력 지시 (모든 과제 끝에 붙임)

```
[출력 형식]
- 단일 HTML 파일로 출력하라. (인라인 CSS 또는 <style> 태그, 외부 의존성 없이 브라우저에서 바로 열려야 함)
- 데스크톱 화면이다. 1440px 너비 기준으로 디자인하라.
- 위 맥락 브리프의 "공통 샘플 데이터"를 실제 콘텐츠로 채워라. 빈 placeholder("Lorem", "내용")로 두지 말 것.
- 기본 상태 + 빈 상태(데이터 0건) 둘 다 보여라. (빈 상태는 화면 하단에 별도 섹션으로 첨부 가능)
- 디자인 결정(색/폰트/레이아웃/컴포넌트)은 전적으로 너에게 맡긴다. 한국 부동산 표기 규칙만 지켜라.
- 설명 문장은 최소화하고 화면 자체로 말하게 하라.
```

## 과제 1 — 매물 목록 화면 (난이도: 상)

```
[과제] Estate ERP의 "매물 목록" 화면을 디자인하라.

이 화면은 중개사가 사무소의 모든 매물을 한눈에 훑고, 원하는 매물을 빠르게 찾고,
한 건을 골라 상세를 확인하기 위한 화면이다.

[반드시 포함할 것]
- 매물 여러 건을 보여주는 목록 (공통 샘플 데이터의 매물 1·2·3 포함, 비슷한 매물 몇 건 더 추가)
- 각 매물의 핵심 정보: 단지명·동호·거래유형(매매/전세/월세)·금액·전용면적·층·확인상태
- 매물 확인상태(미확인/확인됨/계약중/보류/완료)를 시각적으로 구분
- 검색/필터 진입점 (거래유형·지역·가격대 등으로 거를 수 있게)
- 한 매물을 선택했을 때 상세를 보는 방식 (같은 화면 내 패널이든, 별도든 — 네 판단)

[고려할 것]
- 사용자는 40~60대, 한 화면에 정보가 많이 보이는 걸 선호한다.
- 매물이 수십~수백 건일 수 있다.
```

## 과제 2 — 매칭 파이프라인 화면 (난이도: 중)

```
[과제] Estate ERP의 "매칭" 화면을 디자인하라.

매칭은 매수자의 구매 희망조건과 매물을 연결해서, "제안 → 매수자 접촉 → 현장안내 →
소유자 접촉 → 협상 → 거래생성 → 종료" 단계로 거래까지 끌고 가는 파이프라인이다.

[반드시 포함할 것]
- 매칭 건들이 어느 단계에 있는지 한눈에 보이는 구조
- 위 7단계를 모두 표현
- 각 매칭 1건의 정보: 어떤 매물 ↔ 어떤 매수자, 현재 단계, 단계 경과일(예: 3일째)
- 공통 샘플 데이터의 박매수(매수자)와 매물들을 엮어 매칭 5~8건을 여러 단계에 배치
- 한 매칭을 클릭했을 때 무엇을 보여줄지 (상담 이력, 다음 액션 등)

[고려할 것]
- 단계 이동이 잦다. 단계를 옮기는 인터랙션을 어떻게 할지 보여줘라.
```

## 과제 3 — 거래 + 수수료 화면 (난이도: 상)

```
[과제] Estate ERP의 "거래 상세" 화면을 디자인하라.

거래(Deal)는 매칭이 성사된 뒤 실제 계약·정산까지 가는 단계다. 이 화면의 핵심은
수수료 계산이다. 한국 중개 수수료는 매도측과 매수측에서 각각 받고, 공동중개(다른
사무소와 함께 중개)면 상대 중개사 몫도 따로 기록한다.

[반드시 포함할 것]
- 거래 1건의 기본 정보: 대상 매물, 매도인, 매수인, 최종 거래가, 현재 단계(선택/계약금/계약/완료/종료)
- 수수료 계산 영역:
  - 매도측 수수료 (요율 % + 금액)
  - 매수측 수수료 (요율 % + 금액)
  - 수수료 총액 + 부가세
  - 공동중개일 때 상대 중개사 몫 (별도)
- 거래에 참여한 직원별 수수료 배분 (예: 이중개 60%, 사장님 10%)
- 공통 샘플 데이터의 매물 1(래미안고덕, 15억 8,000)을 거래 대상으로 사용

[고려할 것]
- 거래가를 넣으면 수수료가 계산되는 흐름이다.
- 금액이 많이 등장한다. 한국식 금액 표기를 정확히 지켜라.
```

## 과제 4 — 수수료 캐시플로우 대시보드 (난이도: 상)

```
[과제] Estate ERP의 "수수료 캐시플로우" 대시보드를 디자인하라.

이 화면은 사장님이 가장 자주 보는 화면이다. 이번 달 수금 예정·완료 금액과 사무소
고정비를 보고 순이익을 파악한다.

[반드시 포함할 것]
- 이번 달 요약: 수금 완료액, 수금 예정액, 고정비, 순이익(수금완료 − 고정비)
- 수금 건 목록 — 각 건의 수금 상태(대기/수금완료/연체/부분수금/면제)를 구분
- 수금 예정일이 언제인지 (잔금일·수금일을 시간 순 또는 달력으로)
- 거래별로 누구에게(매도/매수) 얼마를 받는지
- 수금 건 8~12개를 여러 상태에 분포시켜 채워라

[고려할 것]
- 사장님은 "이번 달 얼마 들어오고 얼마 남나"를 3초 안에 알고 싶어한다.
- 연체된 수금은 눈에 띄어야 한다.
```

## 과제 5 — 공동중개 네트워크 화면 (난이도: 상, 차별화 기능)

```
[과제] Estate ERP의 "공동중개 네트워크" 화면을 디자인하라.

이 기능은 카카오톡 그룹방을 대체한다. 여러 중개사무소가 "중개방"에 모여 자기 매물을
공유하고, 다른 사무소가 그 매물에 문의해서 공동중개로 거래한다. 핵심은 매물을 공유할
때 단지명·동·호·가격 등을 어디까지 공개할지 직접 고르는 "마스킹"이다. (다른 사무소가
매물을 빼갈 수 있어서)

[반드시 포함할 것]
- 참여 중인 중개방 목록 (예: "강동구 공동중개", "고덕 신축 전문")
- 한 방의 내부: 공유된 매물들의 피드 + 사무소 간 채팅
- 매물을 공유할 때 공개 범위를 고르는 UI (단지명·동·호·가격·층 각각 공개/비공개 토글)
- 마스킹된 매물 카드가 어떻게 보이는지 (예: 동·호는 가려지고 단지·가격만)
- 다른 사무소의 문의를 수락/거절하는 흐름

[고려할 것]
- 익숙한 메신저 단체방의 느낌과, 구조화된 매물 데이터를 어떻게 결합할지가 관건이다.
```

## 선택 과제 (시간 되면) — 앱 전체 셸

```
[과제] Estate ERP의 앱 전체 골격(네비게이션 + 상단 바)을 디자인하라.
대시보드 1개 화면을 본문에 넣어 전체 틀이 어떻게 보이는지 보여라.

[반드시 포함할 것]
- 좌측 네비게이션: 대시보드·매물·연락처·구매조건·매칭·거래·계약·캐시플로우·태스크·캘린더·AI운영·네트워크·직원관리·설정
- 상단 바: 현재 사무소 표시(멀티테넌시 — 사무소 전환 가능해야 함), 전역 검색, 알림, 사용자 메뉴
- 본문: 대시보드 (오늘 할 일, 이번 주 잔금일, 최근 매물/매칭, 수금 현황 요약 등)

[고려할 것]
- 메뉴가 14개로 많다. 어떻게 그룹핑하고 정리할지가 디자인 역량을 가른다.
```
