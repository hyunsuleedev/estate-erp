# Estate ERP — 맥락 브리프 (디자인 테스트용)

> **이 문서의 역할**: 백지(가이드 없음) 디자인 테스트에서 **모든 모델에게 동일하게** 붙이는 프로젝트 설명이다.
> 여기에는 *무슨 제품인지·누가 쓰는지·각 화면이 뭘 하는지·데이터가 어떻게 생겼는지*만 담는다.
> **색·폰트·레이아웃·컴포넌트·간격 같은 디자인 결정은 일부러 뺐다** — 그게 바로 모델이 스스로 풀어야 할 테스트 대상이다.
>
> 단, 한국 부동산 도메인의 **표기 규칙**(금액·면적·주소)은 "디자인 취향"이 아니라 "도메인 사실"이므로 포함한다. 이걸 빼면 모델이 한국 사용자에게 어색한 결과를 내도 그게 능력 부족인지 정보 부족인지 구분할 수 없다.

---

## 1. 제품이 무엇인가

**Estate ERP — 대한민국 부동산 중개사무소를 위한 통합 데스크톱 ERP.**

매물·고객·상담·매칭·거래·계약·일정·수수료 정산·공동중개 네트워크를 하나의 시스템에서 운영한다. 한국 중개사무소가 지금 여러 도구(엑셀·카톡·메모장·CTI·네이버 부동산)에 흩어서 하는 일을 한 앱으로 통합하는 것이 목표다.

- **플랫폼**: Electron 데스크톱 앱이 메인 (해상도 1440×900 이상 가정). 웹은 보조.
- **국가/언어**: 대한민국, 한국어 UI 필수.
- **성격**: B2B SaaS. 광고 노출 없는 순수 업무 효율화 도구.

## 2. 누가 쓰는가

- **Primary**: 3~20명 규모의 중개법인/팀. 사장님(owner) + 실장(manager) + 소속공인중개사(agent).
- **Secondary**: 1인 중개사.
- **연령대**: 40~60대가 주력. 엑셀 스타일 표에 익숙하고, 한 화면에 정보가 많이 보이는 것을 선호한다. 전화 업무가 잦다.
- **멀티테넌시**: 한 사용자가 여러 사무소에 속할 수 있고, 모든 데이터는 "어느 사무소"인지로 격리된다.

## 3. 핵심 데이터 구조 (디자인에 필요한 만큼만)

```
Site(단지/건물) → Dong(동) → Unit(호) → Property(관리단위) → Listing(매물)
                                                          │
Contact(사람) ── BuyerRequirement(구매희망) ── Match ──→ Deal → Contract
                                                          │
                                                   CommissionPayment(수수료 수금)
```

| 엔터티 | 의미 |
|---|---|
| **Site** | 래미안고덕 같은 아파트 단지·빌라·상가·토지까지 모든 부동산 위치 |
| **Unit** | 한 호실 (예: 101동 3501호) |
| **Listing** | 실제 "매물" — 가격, 거래유형(매매/전세/월세), 확인상태 |
| **Contact** | 사람 1명. 소유자·매수자·세입자가 한 테이블에 들어가고 관계로 역할이 정해짐 |
| **BuyerRequirement** | 매수자의 구매 희망조건 (지역·예산·면적·필수조건) |
| **Match** | 구매조건 ↔ 매물 연결, 단계형 파이프라인 |
| **Deal** | 거래 진행 — 수수료를 매도측/매수측/공동중개로 분리 기록 |
| **Contract** | 계약서 상세 — 계약금/중도금/잔금 스케줄 |
| **CommissionPayment** | 수수료 수금 추적 (사장님의 캐시플로우) |
| **Proposal** | AI·규칙엔진이 만든 제안 — 사람이 승인해야 실행됨 (자동 실행 아님) |

## 4. 핵심 상태 파이프라인 (모든 모델이 같은 값을 써야 함)

각 엔터티는 단계형 상태를 가진다. **샘플 화면을 그릴 때 아래 정확한 단계명/한글 라벨을 사용하라.**

- **매물 확인상태** (Listing): `미확인 → 확인됨 → 계약중 → 보류 → 완료`
- **매칭** (Match): `내부 후보 → 고객 관심 → 임장 가능 확인 → 현장안내 → 협상 → 거래생성 → 종료`
- **거래** (Deal): `선택 → 계약금 → 계약 → 완료 → 종료`
- **계약** (Contract): `초안 → 서명 → 계약금납부 → 잔금납부 → 등기완료`
- **수금** (CommissionPayment): `대기 → 수금완료 / 연체 / 부분수금 / 면제`

## 5. 한국 부동산 표기 규칙 (도메인 사실 — 반드시 준수)

> 이건 디자인 취향이 아니라 한국 사용자가 당연하게 기대하는 표기다. 어기면 즉시 어색해 보인다.

| 대상 | 저장 형태 | 화면 표기 |
|---|---|---|
| **금액** | 만원 단위 정수 (`158000`) | `15억 8,000` — 억/만 분리, 천단위 콤마, 0인 자리 생략. ("1,580,000,000원"이나 "158,000만원"으로 쓰지 말 것) |
| **보증금/월세** | deposit + monthlyRent | `보증금 1억 / 월 80` |
| **면적** | m² (소수) | m² 주 표기 + 평 병기: `84.9m² (25.7평)`. 평 = m² × 0.3025 |
| **주소** | 법정동 코드 + 도로명/지번 | 목록은 축약(`강동구 고덕동`), 단지명 우선. 상세는 전체 도로명 |
| **동·호** | Dong · Unit | `101동 3501호` |
| **전화** | 숫자 | `010-1234-5678` (하이픈) |
| **날짜** | ISO | `2026.06.12` 또는 `6월 12일(목)`. 잔금일 등은 D-day 병기 가능 |

## 6. 공통 샘플 데이터 (모든 화면에서 이 값을 쓰면 비교가 쉬움)

화면에 실데이터 예시가 필요하면 아래를 사용하라. (가짜로 채우지 말고 이 세트를 재사용)

- **사무소**: 고덕공인중개사사무소
- **매물 1**: 래미안고덕 101동 3501호 / 매매 / 15억 8,000 / 전용 84.9m²(25.7평) / 35층 / 확인됨
- **매물 2**: 고덕그라시움 203동 1502호 / 전세 / 보증금 9억 / 전용 59.9m²(18.1평) / 15층 / 미확인
- **매물 3**: 강동롯데캐슬 상가 1층 / 월세 / 보증금 5,000 / 월 250 / 전용 33m²(10평) / 계약중
- **소유자**: 김집주인 (소유 50% 지분, 실거주, VIP 태그)
- **매수자**: 박매수 (예산 14억~16억, 고덕동 희망, 전용 84m² 이상, 급함)
- **담당 중개사**: 이중개 (소속공인중개사)

## 7. 무엇을 빼고 무엇을 줬는지 (테스트 설계 메모)

| 줬다 (맥락·도메인 사실) | 뺐다 (디자인 결정 = 테스트 대상) |
|---|---|
| 제품 정체성·사용자·데이터 구조 | 색 팔레트 / 브랜드 컬러 |
| 상태 파이프라인 단계명 | 폰트 / 타이포 스케일 |
| 한국식 금액·면적·주소 표기 | 레이아웃 (목록+패널? 칸반? 그리드?) |
| 공통 샘플 데이터 | 컴포넌트 형태 (카드? 행? 뱃지 스타일?) |
| 각 화면의 목적(과제 프롬프트에서) | 앱 셸 구조 / 네비게이션 |
| | 간격·라운드·그림자 / 정보 밀도 |

이 경계가 테스트의 공정성을 만든다. 모든 모델이 **같은 문제**를 풀되, **디자인은 각자** 끌어낸다.
