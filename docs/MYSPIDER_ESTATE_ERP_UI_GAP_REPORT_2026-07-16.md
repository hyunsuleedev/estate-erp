# MySpider II 대비 Estate ERP UI·기능 갭 분석 보고서

- 작성일: 2026-07-16
- 비교 대상: MySpider II 1.3.9.9 / Estate ERP `main` (`0c675a1`)
- 기준 문서: `docs/마이스파이더V2분석.md`
- 검증 원칙: 양쪽 프로그램 모두 조회·탐색·보기 전환만 수행. 등록, 저장, 수정, 삭제, 상태 변경, 메시지 전송은 수행하지 않음.

## 1. 결론

Estate ERP는 MySpider를 그대로 복제하는 제품이 아니라, 매물 → 매칭 → 거래 → 계약 → 수금/정산을 하나의 데이터 흐름으로 연결하는 현대적인 CRM/ERP에 더 가깝다. 특히 매물·연락처 빠른 확인 패널, 단지/호수 맥락, 매칭의 4가지 보기, 거래 파이프라인, 계약 상세와 문서 허브, 신고 기한과 대금 일정 연결은 현재 Estate ERP의 분명한 강점이다.

반대로 MySpider가 장기간 현장에서 다듬은 “한 화면에서 최대한 많이 보고 바로 처리하는 업무 도구”의 장점은 아직 부족하다. 가장 큰 차이는 다음 다섯 가지다.

1. 전역 검색과 빠른 등록 범위가 좁다.
2. 매물·고객 목록의 정보 밀도, 저장된 보기, 고정 열, 즉시 실행 기능이 부족하다.
3. 통화·녹취·SMS·메모·쪽지 흐름이 한 곳에 통합되어 있지 않다.
4. 공개 매물/공동중개 네트워크와 매수 의뢰 공유는 실사용 검증이 어려운 초기 상태다.
5. 새 환경에서 데스크톱을 안정적으로 실행하는 개발·배포 진입 경로가 완성되지 않았다.

따라서 단기 목표는 MySpider의 모든 메뉴를 복제하는 것이 아니라, Estate ERP의 강한 데이터 흐름은 유지하면서 현장 사용자가 매일 반복하는 검색·전화·등록·상담·매물 확인 동선을 한두 번의 조작으로 줄이는 것이다.

## 2. 검증 범위와 방법

### 실제 화면 검증

MySpider에서는 다음 주요 화면을 직접 열어 구조와 기능을 확인했다.

- 알림판, 내물건, 공개물건, 손님알림, 고객관리
- 문서관리, 마이콜, 일정관리, 입주고객 배치표
- 쪽지관리, 환경설정, 관리자

Estate ERP에서는 29개 라우트와 핵심 하위 흐름을 실제 Electron 창에서 확인했다.

- 대시보드, 업무함, 업무, 캘린더
- 매물장, 관리단지, 광고노트, 내 광고
- 연락처, 구매고객, 상담기록, 녹취/통화 화면, CTI 통화 로그
- 매칭, 거래, 계약
- 수금/정산 대시보드, 원장, 공동중개 수수료, 직원 정산, 내 정산, 비용
- 중개방, 파트너 중개사
- 직원, 업체 디렉토리, 자료실, 사진 자료실, 설정

추가로 아래 읽기 전용 동작을 검증했다.

- 매물 행 더블클릭 → 빠른 확인 패널
- 관리단지 선택 → 테이블/배치표 전환 → 호수 상세
- 연락처 행 선택 → 빠른 확인 패널
- 매칭 고객별/매물별/단계별/칸반 전환
- 거래 보드/리스트 전환
- 계약 상세 → 요약, 당사자, 문서 허브, 거래 정보, 이력
- 캘린더 월/주/일/일정 전환
- 전역 검색 실행 및 결과 확인
- 빠른 등록 메뉴 열기

### 검증 결과 요약

- 확인한 라우트에서 400/500 계열 API 오류는 발견되지 않았다.
- Desktop TypeScript 검사(`tsc --noEmit`)는 통과했다.
- 데이터 변경이 일어나는 버튼은 실행하지 않았다.
- 전화 발신, 실제 CTI 수신, 녹음, SMS, 외부 공개방 참여, 등기 발급처럼 외부 시스템 또는 과금/전송이 연결된 기능은 실행하지 않았다.
- 빈 데이터 화면은 보기 전환과 UI 구조까지만 검증했으며 실제 데이터 처리의 완결성은 판단에서 제외했다.

## 4. Estate ERP의 강점

### 4.1 맥락을 유지하는 빠른 확인 패널

매물과 연락처 목록에서 행을 열면 현재 화면을 떠나지 않고 오른쪽 패널에서 핵심 정보를 확인할 수 있다. 단순 상세가 아니라 “지금 확인할 것”, 최근 상담 부재, 미확인 거래, 연결 매물/구매요건 같은 후속 행동을 함께 보여준다. MySpider의 높은 정보 밀도보다 화면은 덜 복잡하면서도 업무 누락을 줄이는 방향은 더 좋다.

개선 시 이 패턴을 구매고객, 상담, 통화, 매칭, 거래에도 일관되게 확장하는 것이 좋다.

### 4.2 단지 → 동 → 호수 흐름

관리단지의 왼쪽 목록, 테이블/배치표 전환, 점유상태·만기/변동 보기, 호수 상세가 자연스럽게 연결된다. 호수 상세에서 매물, 상담, 소유자/세입자, 등기/문서를 한 문맥으로 보는 구조는 MySpider보다 데이터 모델 측면에서 우수하다.

다만 검증 데이터가 1개 호수뿐이어서 MySpider처럼 수십 층·여러 라인·수백 호수가 있는 단지에서 스크롤, 렌더링, 색상 구분, 검색 속도가 유지되는지는 별도 성능 테스트가 필요하다.

### 4.3 매칭과 거래 파이프라인

매칭은 고객별·매물별·단계별·칸반 네 가지 보기가 실제로 전환되며, 제안 → 고객연락 → 임장 → 집주인연락 → 협상 → 거래전환이 명확하다. 거래도 보드와 리스트를 모두 제공한다. MySpider의 손님알림/계약 중심 기능보다 업무 상태가 더 명확하고, 이후 자동화와 통계의 기반도 좋다.

### 4.4 계약 상세와 문서 허브

현재 계약 상세는 보고서 기준으로 가장 완성도가 높은 영역이다.

- 작성중 → 서명완료 → 계약금완료 → 잔금완료 → 등기완료 단계
- 거래신고 기한 경고
- 계약금/중도금/잔금 타임라인
- 다수 당사자와 대리인, 공동중개 사무소 구조
- 필수/선택 문서와 누락 상태
- 작성 문서, 사본, 수정 흐름
- 연결 거래/매물/연락처와 감사 이력

기존 분석 문서에서 제안한 ContractDocument/Template 성격의 기능은 현재 코드와 UI에 이미 상당 부분 구현되어 있다. 이 영역은 다시 새로 설계하기보다 인쇄 정확도, 전자계약, 신고 연계, 문서 보존과 권한을 중심으로 고도화해야 한다.

### 4.5 캘린더와 재무 일정 연결

월/주/일/일정 보기가 모두 정상 전환되며 일반·임장·계약·미팅·업무뿐 아니라 계약일·중도금일·잔금일·수금예정 오버레이를 제공한다. MySpider의 일정관리와 비교해도 구조적으로 뒤지지 않는다.

## 5. 주요 부족 사항

### P0. 실행 안정성과 첫 화면 신뢰성

#### 데스크톱 개발 실행이 새 환경에서 바로 되지 않음

- `apps/desktop/.env`가 없고 인증 렌더러에 필요한 공개 Clerk 키가 주입되지 않으면 앱이 스플래시에서 진행되지 않는다.
- Corepack을 통한 pnpm 실행은 가능했지만 Electron Forge가 자식 프로세스에서 `pnpm`을 직접 찾지 못해 `ENOENT`로 실패했다.
- Forge 경로에서는 Vite 의존성 스캔 중 서버가 재시작/종료됐다는 오류가 발생했으나, Vite와 Electron을 분리 실행하면 동작했다.

개선안:

- 저장소 루트에 `packageManager` 버전을 고정하고 Windows용 부트스트랩 스크립트에서 Corepack 활성화 여부를 검사한다.
- 공개 환경변수의 위치와 발급 절차를 명확히 문서화하고, 비밀키는 절대 데스크톱에 전달하지 않는다.
- `pnpm dev:desktop` 한 명령으로 인증 설정 검사 → Vite 준비 확인 → Electron 시작이 순서대로 보장되어야 한다.
- CI에서 Windows fresh-clone smoke test를 추가한다.

완료 기준:

- 새 Windows 계정에서 문서대로 3개 이하 명령으로 로그인 화면까지 실행된다.
- 누락된 환경변수가 있으면 10초 이내에 변수명, 해결 방법, 재시도 버튼을 표시한다.

#### 스플래시가 실제 상태와 무관하게 완료처럼 보임

인증 설정이 누락된 상태에서도 계정/사무소 확인 단계가 완료된 것처럼 표시됐다. 사용자는 앱이 멈춘 것인지 네트워크가 느린 것인지 알 수 없다.

개선안:

- 각 단계는 실제 Promise 상태와 연결한다.
- `pending/success/error`를 분리하고 오류 상세, 재시도, 로그 복사 기능을 제공한다.
- 자식 라우트 새로고침 때 전체 스플래시를 오래 보여주지 말고 앱 셸과 페이지 스켈레톤을 분리한다.

### P0. 전역 검색 범위와 응답성

전역 검색은 현재 연락처, 단지, 매물을 대상으로 한다. 실제 `고덕` 검색은 로컬 환경에서도 결과까지 약 3초가 걸렸다. 계약, 거래, 구매고객, 상담, 업무, 문서는 검색되지 않는다.

개선안:

- 최소 검색 대상: 연락처/전화번호, 구매고객, 단지/동/호, 매물, 상담, 매칭, 거래, 계약, 업무, 문서.
- 결과는 엔티티별 그룹, 최근 열람, 키보드 이동, 새 탭/빠른 패널 열기를 지원한다.
- 250ms debounce, 이전 요청 취소, 서버 검색 인덱스, 상위 결과 제한을 적용한다.
- 한글 초성·전화번호 뒷자리·주소 토큰 검색을 지원한다.

완료 기준:

- 일반 검색 p95 700ms 이하, 첫 결과 500ms 이내.
- 검색 결과에서 엔티티 상세까지 키보드만으로 이동 가능.

### P0. 숨은 경로와 명칭 불일치

- 사이드바의 `통화기록`은 녹취/STT 화면(`/calls`)으로 연결되며 실제 CTI CallLog는 `/calls/logs`에 따로 있다.
- `/calls/logs`와 `/documents/photos`를 직접 열면 탭 제목에 사람이 읽는 이름 대신 경로가 표시됐다.
- `자료실`은 계약 문서가 아니라 공부서/사진 영역인데, `문서`라는 용어가 계약 문서 허브와 중복된다.
- 매물 화면은 사이드바에서 `매물장`, 브라우저 탭에서 `매물관리`로 표현된다.

개선안:

- 통화 메뉴를 `통화 내역`과 `녹취/전사`의 하위 탭으로 통합한다.
- 모든 자식 라우트에 공통 route metadata를 적용한다.
- `계약 문서`, `공부서`, `매물 사진`, `일반 자료`의 정보 구조를 분리한다.
- 제품 용어 사전을 만들고 사이드바·탭·페이지 제목·검색 결과에서 동일한 명칭을 사용한다.

### P0. 위험 작업과 비활성 기능의 설명

- 계약 목록에서 `삭제`가 일반 작업과 같은 수준으로 노출된다.
- `계약 생성`은 비활성화되어 있지만 이유나 다음 행동이 표시되지 않는다.
- 넓은 테이블의 작업 열이 오른쪽 끝에 있어 1440×900에서도 가로 스크롤이 필요하다.

개선안:

- 삭제는 더보기 메뉴로 이동하고 권한, 확인 문구, 감사 로그를 적용한다.
- 비활성 버튼에는 “계약 가능한 거래가 없음”처럼 이유와 해결 경로를 표시한다.
- 핵심 식별 열과 작업 열을 고정하고, 위험 작업은 항상 분리한다.

### P1. 매물장의 현장 정보 밀도

MySpider 내물건은 한 화면에서 거래종류, 공개 상태, 확인 상태, 소유자/세입자, 상담, 메모, 만기, 관심/추천/소개를 동시에 본다. Estate ERP는 필터와 빠른 상세가 좋지만, 핵심 열만으로도 가로 스크롤이 발생하고 현장 상태가 여러 화면에 흩어져 있다.

개선안:

- `간편/기본/고밀도` 보기 모드를 제공한다.
- 사용자별 이름 있는 보기 프리셋과 열 순서/너비/고정/숨김을 서버에 저장한다.
- 기본 고정 열: 거래유형, 단지/동/호, 가격, 확인상태, 소유자/세입자, 최근상담, 다음 업무, 만기, 광고 상태.
- 관심, 추천, 소개, 확인 요청, 임대차 만기, 고객 정보 필터를 상단 리본 또는 저장 보기로 제공한다.
- 행 선택 시 빠른 패널뿐 아니라 전화, 상담 기록, 업무 추가를 바로 실행할 수 있게 한다.

완료 기준:

- 1440×900에서 기본 핵심 열과 작업 버튼이 가로 스크롤 없이 보인다.
- 사용자가 만든 보기가 다른 PC에서도 복원된다.

### P1. 빠른 등록과 전역 업무 바

Estate ERP의 빠른 등록은 매물, 연락처, 일정, 업무 네 가지다. MySpider는 계약, 알림, 고객, SMS, 메모, 녹취, 전화까지 상시 접근한다.

개선안:

- 빠른 등록에 구매고객, 상담, 매칭, 거래, 계약을 추가한다.
- CTI가 연결된 환경에서는 전화/통화 기록/녹취가 같은 바에서 보이게 한다.
- 최근 사용 4개를 앞에 배치하고 나머지는 사용자별로 재정렬한다.
- 현재 보고 있는 매물/연락처/호수 문맥을 등록 폼에 자동 전달한다.

### P1. 고객 목록과 그룹 관리

연락처 목록은 연결 매물/요건을 잘 보여주지만, 테스트 데이터 16명 중 분류 그룹 카운트는 모두 0이었다. MySpider는 초성 탭, 사용자 그룹, 고객 유형, 동의 상태, 최종 상담을 한 화면에 제공한다.

개선안:

- 관계와 구매요건/매물 연결을 이용해 `소유자`, `매수/투자`, `임차`, `거래처` 추천 분류를 제공한다.
- 수동 그룹과 시스템 분류를 구분한다.
- 초성/전화 뒷자리 빠른 필터, 개인정보 동의 상태, 최근 상담일, 다음 후속 업무를 기본 열에 추가한다.
- 다중 전화번호 기능은 이미 구현되어 있으므로 목록과 검색 결과에서 대표/보조 번호를 명확히 표시한다.

### P1. 통화·녹취·상담 통합

코드와 숨은 라우트에는 CallLog와 CTI 팝업이 존재하지만, 현재 메뉴 구조에서는 사용자가 녹취 화면과 실제 통화 이력을 구분하기 어렵다.

개선안:

- 하나의 통화 허브 안에 전체/수신/발신/부재중, 녹취, 전사, 상담 연결 상태를 제공한다.
- 통화 행에서 연락처 연결, 새 연락처, 상담 생성, 매물/구매요건 연결을 한 흐름으로 처리한다.
- 부재중 전화는 업무함 또는 Task로 자동 제안한다.
- CTI가 없는 PC에서는 기능 상태와 설정 방법을 명확히 보여준다.

### P1. 설정 페이지 탐색성

설정은 사무소, 직원, 수수료, 계약 템플릿, 고정비, AI 직원, MCP 키까지 풍부하지만 한 페이지가 지나치게 길다. 저장 버튼도 여러 구역에 흩어져 변경 범위를 파악하기 어렵다.

개선안:

- 왼쪽 섹션 내비게이션과 설정 검색을 추가한다.
- `사무소/계정/권한/수수료/계약문서/자동화/연동/화면`으로 분리한다.
- 각 섹션에 dirty 상태, 변경 취소, 마지막 저장 시각을 표시한다.
- 화면 밀도, 기본 보기, 대시보드 위젯, 알림 채널은 사용자별 설정으로 분리한다.

### P2. 공개 매물·공동중개 네트워크

Estate ERP의 중개방은 공유 매물, 문의, 채팅을 담을 수 있는 좋은 구조지만 현재 계정에는 방과 데이터가 없어 실제 흐름을 검증할 수 없었다. MySpider의 공개물건은 사무소, 중개사, 확인 요청, 공개 상태를 대규모 그리드로 운영한다.

개선안:

- 공개방 찾기 → 참여 → 공유 매물 조회 → 문의 → 채팅 → 공동중개 거래 전환의 샌드박스 시나리오를 만든다.
- 매수 의뢰 공유를 위한 `NetworkBuyRequest` 또는 동등 모델과 UI를 추가한다. 현재 Prisma 스키마 검색에서는 해당 모델을 확인하지 못했다.
- 공개 범위, 만료, 철회, 사무소 신뢰 상태, 중복 매물 병합, 개인정보 노출 기준을 정의한다.
- 공개 매물 확인 요청과 응답 SLA를 업무함/알림에 연결한다.

### P2. 메시지·SMS·메모

MySpider는 쪽지관리와 SMS/메모 진입점이 독립적으로 있다. Estate ERP는 중개방 채팅은 설계되어 있지만 사무소 내부 쪽지, 고객 SMS 이력, 통합 메모함은 주요 화면에서 확인되지 않았다.

개선안:

- 고객별 커뮤니케이션 타임라인에 통화, SMS, 상담, 메모, 이메일을 통합한다.
- 내부 메시지는 Task 멘션/알림과 중복되지 않도록 목적을 명확히 정한다.
- 전송 기능은 템플릿, 수신 동의, 실패/재시도, 감사 로그를 갖춘 뒤 공개한다.

### P2. 대시보드와 알림 개인화

MySpider는 알림판에 표시할 항목과 팝업 기간을 사용자가 선택할 수 있다. Estate ERP 대시보드는 후속 행동 중심으로 더 좋지만 개인화는 부족하다.

개선안:

- 위젯 표시/숨김, 순서, 크기, 기본 기간을 사용자별 저장한다.
- 임대차 만기, 미확인 매물, 신고 기한, 부재중 전화, 광고 불일치를 한 알림 정책으로 통합한다.
- 알림 클릭 시 해당 엔티티의 빠른 확인 패널과 해결 행동으로 바로 이동한다.

## 6. 기존 분석 문서에서 갱신할 내용

`마이스파이더V2분석.md`의 제안 중 아래 항목은 현재 코드/스키마/화면에 이미 구현되어 있어 “미구현” 목록에서 제외하거나 상태를 갱신해야 한다.

- `CallLog`: 별도 Prisma 모델과 CTI 로그 UI가 존재함.
- `ContactPhone`: 다중 전화번호 모델과 편집기가 존재함.
- `ContractDocument`, `ContractDocumentTemplate`, revision 성격의 모델과 문서 엔진이 존재함.
- 캘린더 색상, 상태 계산, 월/주/일/일정 UI가 존재함.
- 외부 광고 가격과 광고 레코드 추적 구조가 존재함.

아래 항목은 여전히 보강 또는 존재 여부를 확정할 필요가 있다.

- 공동중개 매수 의뢰 공유 모델과 UI
- 사용자별 영구 저장 열 프리셋/이름 있는 보기
- 대시보드 레이아웃 개인화
- 팝업/반복/채널별 알림 정책
- SMS·메모·통화·상담 통합 타임라인

## 7. 권장 업데이트 순서

### 1단계 — 신뢰성과 명칭 정리 (1~2주)

- 데스크톱 fresh-clone 실행 경로와 환경변수 진단 완성
- 실제 상태 기반 스플래시와 오류 복구
- `/calls/logs`, `/documents/photos` 탭 제목 수정
- 통화/녹취, 자료실/계약문서, 매물장/매물관리 명칭 통일
- 비활성 계약 생성 사유와 삭제 UI 보호

### 2단계 — 매일 쓰는 동선 단축 (2~4주)

- 전역 검색 대상 확대와 성능 개선
- 빠른 등록 대상 확대
- 매물 고밀도 보기, 고정 열, 저장 보기
- 연락처 분류/초성/최근상담/다음업무 강화
- 설정 섹션 내비게이션과 화면 개인화

### 3단계 — 커뮤니케이션 허브 (3~5주)

- 통화 내역과 녹취/전사 통합
- 통화 → 연락처 → 상담 → 업무 생성 흐름
- 고객 커뮤니케이션 타임라인
- SMS 템플릿, 수신 동의, 전송 결과, 감사 로그

### 4단계 — 공동중개와 외부 연계 (4~8주)

- 공개방/공유 매물/문의/채팅 E2E 시나리오
- 매수 의뢰 공유
- 전자계약, 신고, 문서 보존, 등기 연계 고도화
- 실제 규모 데이터로 단지 배치표, 매물장, 공개 네트워크 성능 테스트

## 8. 출시 전 회귀 테스트 기준

다음 시나리오는 데이터가 격리된 테스트 사무소에서 자동화해야 한다.

1. 로그인 → 대시보드 → 전역 검색 → 매물 빠른 확인 → 상담 생성.
2. 단지 → 동/호 선택 → 소유자/세입자 확인 → 매물 또는 상담 시작.
3. 연락처 → 구매요건 → 매칭 → 단계 이동 → 거래 전환.
4. 거래 → 계약 생성 → 당사자 입력 → 문서 작성 → 상태 진행.
5. 계약금/중도금/잔금 → 캘린더/수금/정산 반영.
6. CTI 수신/발신/부재중 → CallLog → 연락처/상담/Task 연결.
7. 공유 매물 → 문의 → 채팅 → 공동중개 거래.
8. 사용자 권한별 조회/수정/삭제 차단과 ActivityLog 기록.

성능 기준도 함께 둬야 한다.

- 전역 검색 첫 결과 p95 500~700ms
- 매물 10,000건 필터/정렬 1초 이내
- 단지 2,000호 배치표 최초 표시 1.5초 이내, 스크롤 50~60fps 목표
- 페이지 전환 시 앱 전체 스플래시 금지, 페이지 스켈레톤 200ms 이내 표시

## 9. 최종 판단

Estate ERP의 핵심 경쟁력은 MySpider보다 더 많은 버튼이 아니라, 서로 분리되어 있던 매물·고객·상담·매칭·거래·계약·정산을 한 데이터 그래프로 연결하는 것이다. 현재 계약과 매칭은 이미 이 방향을 잘 보여준다.

다음 업데이트는 새로운 대형 모듈을 늘리기보다 실행 안정성, 전역 검색, 빠른 등록, 매물/고객 고밀도 보기, 통화 통합을 먼저 완성하는 것이 효과가 가장 크다. 이 다섯 가지가 해결되면 MySpider 사용자가 느끼는 “현장에서 바로 찾고 바로 처리하는 속도”를 확보하면서도 Estate ERP의 더 강한 파이프라인 구조를 유지할 수 있다.

## 10. AI파트너(이실장) 추가 비교

### 10.1 조사 범위와 요약

로그인된 AI파트너를 읽기 전용으로 확인했다. 홈, 임장활동, 관리 호실, 임장알림, 매물장, 매물광고, 네이버 모니터링, 공동중개, 사진첩, 고객, 상담내역, 맞춤매물, 일정, 계약, 안심케어와 FAQ를 확인했으며 데이터 등록·수정·삭제와 계약서/공부 발급 같은 상태 변경 행동은 수행하지 않았다.

AI파트너의 가장 큰 강점은 화면 디자인 자체가 아니라 외부 부동산 시장과 법정·광고 업무를 하나의 작업 흐름으로 연결한 점이다. Estate ERP가 내부 업무 파이프라인과 데이터 구조에서 앞선다면, AI파트너는 네이버 광고 변화, 광고 검증, 등기·공부, 현장 사진과 고객 커뮤니케이션을 실제 중개사 업무에 붙이는 완성도가 높다.

### 10.2 AI파트너에서 특히 배워야 할 제품 루프

#### 네이버 모니터링을 “수집 화면”이 아니라 “대응 업무”로 만든다

단지별 매물 수만 보여주면 보고서에 그친다. 신규·삭제·가격 변화·동일 매물·노출 순위·중개사 변화를 매일 비교하고, 자사 매물이 밀렸거나 광고가 종료될 때 담당자에게 업무를 생성해야 한다. 각 변화에는 이전/현재 값, 수집 시각, 출처, 신뢰도와 확인 상태가 남아야 한다.

#### 광고 검증과 신고 예외를 운영 큐로 만든다

광고 등록 성공 여부만으로는 부족하다. 검증중, 검증실패, 종료예정, 거래완료 주소, 신고 미처리 같은 예외를 담당자·기한·원인별로 정렬하고 재검증, 광고 종료, 매물 상태 변경으로 이어지는 해결 동선을 제공해야 한다. 자동 수정은 하지 않고 사람이 승인하도록 설계하는 편이 안전하다.

#### 계약 전 위험 정보를 한곳에서 비교한다

등기부와 각종 공부를 계약 입력 보조 자료로만 쓰지 말고 계약 시점의 스냅샷으로 보존한다. 이후 소유권, 근저당, 가압류 등 주요 항목이 바뀌면 변경 전/후를 비교해 보여주고 담당자의 확인, 고객 안내, 조치 결과를 ActivityLog에 남겨야 한다.

#### 사진을 독립 자료실이 아니라 매물 생성의 시작점으로 본다

모바일 촬영 또는 고객 링크 업로드 → 주소 후보 확인 → 동/호 또는 매물 연결 → 개인정보 모자이크/워터마크 → 광고 채널 선택 → 게시 결과 확인의 흐름이 필요하다. 원본과 편집본을 분리 보존하고 사용자·사무소별 접근 권한과 공유 만료를 적용해야 한다.

#### 초기 도입의 가장 큰 마찰인 데이터 이전을 해결한다

연락처와 매물을 엑셀에서 가져올 때 바로 저장하지 말고 열 매핑, 필수값 검증, 전화번호 정규화, 중복 후보와 병합 결과를 먼저 미리 보여준다. 사용자가 승인한 뒤에만 일괄 반영하고 전체 작업을 되돌릴 수 있는 import batch 단위 감사 기록을 남겨야 한다.

### 10.3 업데이트 우선순위 조정

네이버 매물 변화와 광고 검증은 CP사 또는 공식 제휴·데이터 권한에 의존한다. 등기 자동 발급/변경 감시, 알림톡, 보험도 외부 사업자 계약이 필요하다. 따라서 이 기능들은 현재 제품의 선행 조건이 아니며, 제휴가 확보되기 전에 직접 수집이나 자동 제출을 전제로 구현하지 않는다.

#### P0 — 외부 제휴 없이 완성하는 중개 ERP 코어

- 고객 → 상담 → 매수/임차 요구조건 → 매칭 → 거래 전환의 끊김 없는 화면 흐름
- 매물 상세에서 소유자·세입자·상담·일정·가격 이력·계약 진행을 함께 보는 통합 작업 패널
- BuyerRequirement의 면적·입주일·대출·방/욕실·층·향·구조 조건 확장과 내부 매물 자동 매칭
- 연락처/매물 엑셀 가져오기 사전검증, 전화번호 정규화, 오류행 안내와 중복 병합
- 계약금·중도금·잔금·임대차 만기와 Task/Calendar/Notification의 일관된 연결
- 수기 등기·공부 확인일, 확인자, 첨부문서와 위험 체크리스트 기록
- 전역 검색, 빠른 등록, 저장된 보기, 고정 열과 고밀도 매물/고객 화면

#### P1 — 현장 처리 속도와 자료 관리

- PC/모바일 사진 업로드, 주소·동/호·매물 연결, 원본/편집본 구분과 워터마크
- 통화 → 연락처 → 상담 → 후속 업무 생성과 고객별 커뮤니케이션 타임라인
- 계약서/확인설명서 일괄 출력, 복사, 휴지통 복구와 법정 서식 버전 관리
- 동/호 단위 소유자·점유자·임대차·매물 의뢰 상태와 현장 확인 이력
- 공동중개 공유 매물·문의·채팅의 내부 E2E 완성 및 공개 범위/만료/감사 정책

#### P2 — 제휴가 확보된 뒤 연결하는 외부 서비스

- 공식 CP/API 기반 네이버 매물 신규·삭제·가격·순위·중복 변화 모니터링
- 광고 검증·신고·종료 상태 수신과 예외 처리 큐
- 등기·공부 자동 발급, 주요 권리 변경 감시와 스냅샷 비교
- 알림톡/SMS, 전자계약, 부동산 신고, 법률·보증·보험 연동

P2는 지금 가짜 데이터나 비공식 스크래핑으로 완성된 것처럼 만들지 않는다. 대신 향후 공급자를 교체할 수 있도록 `provider`, `externalId`, `observedAt`, 원본 응답 보관 위치, 동기화 상태와 오류를 담는 어댑터 경계만 설계한다. 현재 개발의 성공 기준은 외부 서비스 수가 아니라 중개사가 보유한 매물·고객·상담·계약 정보를 빠르고 정확하게 처리하는 것이다.

### 10.4 추가 회귀 테스트

운영 데이터와 분리된 테스트 사무소에서 외부 제휴가 필요 없는 핵심 업무부터 다음과 같이 검증한다.

1. 고객 엑셀 사전검증에서 오류행은 저장되지 않고 중복 후보는 승인한 병합 규칙대로만 처리되는지 확인한다.
2. 고객 → 상담 → 매수/임차 요구조건 → 내부 매물 매칭 → 거래 전환 과정에서 연관관계와 담당자가 유지되는지 확인한다.
3. 매물 통합 패널에서 소유자·세입자·가격 이력·상담·일정·계약 상태가 정확히 연결되는지 확인한다.
4. 계약금·중도금·잔금·임대차 만기가 캘린더, 업무와 알림에 중복 없이 반영되는지 확인한다.
5. 수기로 입력한 등기/공부 확인 기록, 위험 체크 항목과 첨부문서가 권한별로 보호되고 ActivityLog에 남는지 확인한다.
6. 사진 업로드부터 주소·동/호·매물 연결, 원본/편집본 분리와 워터마크까지 확인한다.
7. 복합 매수 조건에 맞는 신규 내부 매물이 한 번만 알림되고 조건 변경 시 결과가 재계산되는지 확인한다.

외부 공급자 계약 이후에는 별도의 커넥터 테스트 묶음에서 수집 실패, 지연, 중복 이벤트, 공급자 변경과 재처리를 검증한다.

### 10.5 갱신된 최종 판단

세 제품의 강점은 서로 다르다. MySpider는 데스크톱 고밀도 조작과 통화 중심의 오래된 실무 동선, AI파트너는 외부 매물시장·광고 검증·공부/등기·사진을 묶은 중개업 특화 연결, Estate ERP는 매물→고객→상담→매칭→거래→계약→정산을 잇는 데이터 구조와 확장성이 강하다.

따라서 Estate ERP가 단순히 두 제품의 메뉴를 복제해서는 이기기 어렵다. 당장은 **현장 처리 속도**, **고객·상담·매칭의 연결**, **매물·계약 정보의 정확한 관리**를 먼저 완성해야 한다. 네이버 모니터링, 광고 검증, 등기 자동 감시는 경쟁 제품에서 배울 장기 방향이지만 CP/API와 공식 제휴가 확보된 뒤 연결할 기능이다. 현재 가장 큰 제품 공백은 외부 서비스가 아니라 이미 보유한 고객·매물·업무·계약 데이터를 중개사가 하루 종일 빠르고 안전하게 처리할 수 있는 완성도다.
