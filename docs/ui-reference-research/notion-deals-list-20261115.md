# 거래관리 리스트 — 현재 Notion 화면과 비교 조사

조사일: 2026-11-15. 아래 조사 시점에는 제품 코드와 업무 데이터를 수정하지 않았다. 이후 사용자의 적용 요청에 따라 목록 UI를 변경했으며, 적용 결과는 다음 절에 구분해 기록한다.

## 후속 적용 — 매물관리 테이블 구조, 2026-11-15

사용자의 추가 요청에 따라 로그인된 Electron의 `/properties` 표를 직접 확인하고 거래 목록에 같은 구조를 적용했다.

- 매물 제목을 **단지·동·호** 열로 분리했다. 주소 줄은 표시하지 않는다. 동 구분이 없는 건물의 placeholder 동은 빈값으로 표시한다.
- 공통 `DataTable`의 `propertyListTone`을 사용한다. 실제 헤더 36px/13px, 본문 40px/14px로 측정했다. 단계별 묶음·건수·접기와 단계 변경 메뉴는 유지했다.
- 단일 클릭은 셀 선택, 방향키는 셀 이동, Enter·더블클릭·별도 열기 버튼은 상세 열기다. 단계 메뉴의 키보드 입력은 상세 열기로 전파되지 않는다.
- 헤더 클릭은 오름차순 → 내림차순 → 기본 순서다. 정렬 기준과 열 너비를 단계 그룹끼리 공유한다. 동·호는 숫자 순서를 고려하며, 빈값은 두 정렬 방향 모두 뒤에 둔다. 열 경계 드래그·더블클릭 초기화를 실제 화면에서 확인했다.
- 전체 목록에 가로 스크롤을 하나만 두었다. 1280px 화면에서 표 1232px를 본문 1000px 안에서 스크롤하며 페이지 폭은 1280px로 유지된다.

검증: desktop 타입 검사 통과. 거래 관련 14개 및 공통 테이블 opt-in 검사 6개 통과. 추가 실행한 기존 `data-table.test.ts`는 41개 중 29개 통과, 매물관리 소스를 대상으로 하는 기존 정적 검사 12개 실패. 이번 후속 변경에서는 해당 매물관리·공통 테이블 소스와 기존 테스트를 수정하지 않았다. 실제 Electron에서 셀 선택 → Enter 상세, 단계 메뉴 → 확인창 → 취소, 정렬·너비 조절과 초기화를 확인했다. 업무 데이터 저장은 하지 않았다.

스크린샷과 기존 검사 실패 로그: `/tmp/estate-deals-property-table/`.

## 최초 적용 결과 — 2026-11-15

- 거래 리스트의 주소 줄·순번·짧은 내부 코드·태그 열을 제거했다. 거래유형과 공동중개를 독립된 열로 배치하고, 매물과 다음 일정에 남는 너비를 배분했다.
- 행 높이는 실제 Electron에서 **49.75px → 40px**로 확인했다. 열 제목과 데이터에는 native table 구조를 사용했다.
- 그룹 하단 중복 건수와 혼합 거래유형의 금액 합계를 제거했다. 빈 단계는 기본 접힘이며 사용자가 펼칠 수 있다. 그룹 간격은 20px에서 12px로 줄였다.
- 날짜가 없는 일정의 중복 ‘미정’ 배지를 제거했다. 일정 강조는 셀의 배지 한 곳에 두고, 연체는 destructive, 3일 이내 일정은 warning 토큰을 사용한다.
- 제목에 hover·키보드 포커스 시 보이는 ‘열기’를 추가했다. 제목 버튼에서 Enter로 상세 시트가 열리는 것을 확인했다.
- 단계 셀은 단계 선택 메뉴를 연다. 메뉴 선택은 기존 `onRequestStage`와 페이지의 확인 다이얼로그에 연결했다. 기존 계약서 조건은 변경하지 않았다. 실제 확인창까지 검수한 뒤 취소했으며 업무 데이터의 단계는 저장하지 않았다.
- 목록의 상태 색은 공유 `StatusBadge` 기준을 사용한다. 기존 칸반의 표시 구현은 유지했다. 목록용 정렬·열 설정은 이번 변경 범위에 포함하지 않았다.

검증: desktop `tsc --noEmit` 통과, `deal-view-utils.test.ts`와 `deals-ui.test.ts` **11/11 통과**. 실제 Electron 기본 너비와 임시 1280px 렌더러 뷰포트에서 화면을 확인했다. 1280px에서는 본문 가용 폭 1000px 안에서 1100px 표가 가로 스크롤되며, 페이지 전체 폭은 1280px를 유지했다. 검수 후 기존 1725 × 992 렌더러 크기로 복구했다.

적용 후 스크린샷·측정·변경 전 소스 사본: `/tmp/estate-deals-list-implementation/`. 단계 변경 메뉴와 확인창의 연결을 검증했지만 실제 단계 저장이나 서버 정책 변경을 시험한 것은 아니다.

## 판단

거래 리스트의 개선 우선순위는 **행의 정보량, 열 너비 배분, 셀의 동작**이다. 현재도 얇은 경계선과 단계별 그룹을 사용하지만, 반복 주소·건수·빈값 안내가 공간을 쓰고 보조 정보인 태그 열이 남는 너비를 모두 받는다.

사용자가 조사 중 **“상세 주소는 화면에서 필요없어”**라고 확인했다. 거래 리스트에서 주소 줄을 제거하고, 단지명·동·호를 한 줄로 표시하는 것을 제안의 기준으로 삼는다. 데이터 삭제나 다른 화면의 주소 제거를 의미하지 않는다.

## 확인한 대상과 방법

- Notion: 실행 중인 데스크톱 앱 **7.42.3**, Electron 44.9.1. 현재 페이지는 **작업 트래커 | 모든 작업**이다. 이 화면은 상태로 그룹화한 **테이블 뷰**다.
- EstaitFlow: 로그인된 실제 Electron의 `http://localhost:5175/deals`, 리스트 보기, 현재 7건. 브라우저 검수를 먼저 시도했으나 로그인이 필요했고, 사용자가 이번에는 로그인된 Electron을 사용하도록 명시했다.
- Notion은 REA 6.8.0으로 현재 대상 탐색 → 페이지·접근성·스크립트 수집 → 스크립트 내보내기 → 선택한 JavaScript 두 파일의 정적 분석을 수행했다.
- Notion의 실제 hover·상태 메뉴 열기, CSS 측정, 스크린샷은 동일 렌더러에 대한 직접 CDP 관찰이다. REA가 해당 입력 시나리오를 기록한 것으로 표현하지 않는다.
- EstaitFlow는 실제 렌더러에서 리스트 전환, 행 hover, 단계 셀 클릭, 액션 메뉴 열기를 확인하고 현재 소스와 대조했다. 메뉴와 상세창은 닫았다. 상태 선택·저장·삭제는 수행하지 않았다.

두 앱의 창 너비는 다르다. 아래 치수는 스크린샷 픽셀이 아니라 CSS px이며, 전체 화면의 보이는 행 수를 같은 조건의 성능·밀도 비교로 사용하지 않는다.

## 현재 거래 리스트에서 확인한 문제

### 1. 주소 줄이 모든 행을 약 50px로 만든다

현재 일곱 행 모두 같은 지역 주소가 두 번째 줄에 반복된다. 매물명은 단지·동·호만으로 식별 가능한 상태다. 주소가 필요 없다는 사용자 확인에 따라 해당 보조 줄을 없애고, **40px 안팎의 한 줄 행**을 목표로 하는 것이 타당하다. 글자 크기를 줄여 밀도를 확보할 필요는 없다.

근거: [행 구현](../../apps/desktop/src/renderer/routes/_authenticated/deals/-deal-list.tsx), `DealListRow`의 매물 셀. 현재 DOM 실측은 `deals-metrics.json`에 보존했다.

### 2. 가장 넓은 열이 ‘태그’다

현재 본문 표 폭은 1445px이다. 매물은 260px 고정, 태그는 `flex-1`이라 **405px**다. 그 안에는 거래유형, UUID 앞부분으로 만든 짧은 코드, 공동중개 여부가 섞여 있다. 넓은 창에서 태그 오른쪽은 비고처럼 비어 보이고, 핵심 정보인 매물명·금액·일정의 폭은 그대로다.

반대로 소스상 최소 폭 1100px에서는 다른 고정 열 1040px를 제외하면 태그에 약 60px가 남는다. `flex-wrap` 때문에 추가 줄이 생길 수 있다. 이 좁은 폭의 결과는 이번 런타임에서 측정하지 않았다.

제안은 ‘거래유형’과 ‘공동’을 명확한 항목으로 분리하고, 순번과 짧은 내부 코드는 기본 목록에서 생략하는 것이다. 남는 폭은 매물과 다음 일정에 우선 배분한다. 내부 코드가 필요한 운영 흐름이 있다면 상세나 복사 메뉴에 둘 수 있다.

### 3. 그룹의 안내가 실제 행만큼 반복된다

데이터가 있는 그룹마다 32px 그룹 머리, 4px 간격, 36px 열 제목, 32px 하단 건수, 20px 그룹 간격이 있다. 행을 제외해도 그룹당 124px다. 그룹 머리에 이미 건수가 있어 하단의 ‘거래 2건’은 같은 정보를 반복한다.

빈 가계약 그룹도 32px 머리와 36px 안내, 4px 간격을 차지한다. 현재는 빈 단계가 무엇인지 머리의 ‘0’으로 알 수 있으므로 기본 접힘이 충분하다.

현재 첫 그룹 머리부터 마지막 그룹 하단 건수까지 높이는 약 **916px**다. 그중 7개 데이터 행은 약 348px다. 그룹 구조가 항상 나쁘다는 뜻은 아니며, 소량 데이터에서 반복 안내가 특히 두드러지는 근거다.

제안: 그룹 머리의 단계·건수와 접기는 유지, 하단 건수는 제거, 빈 그룹은 기본 접힘, 그룹 간격은 약 12px. 각 그룹의 열 제목은 우선 유지한다. 단일 sticky 헤더로 통합하는 것은 별도 설계 선택이며, 현재 Notion이 그렇게 동작한다는 뜻은 아니다.

### 4. 빈값과 경고의 의미를 더 분명하게 할 수 있다

다음 일정이 없는 행은 현재 **‘일정 미정’ + ‘미정’ 배지**를 함께 표시한다. 하나의 ‘일정 미정’으로 정리한다. 지급이 모두 완료된 경우와 날짜만 없는 경우는 데이터로 구별 가능한 범위에서 별도 문구를 사용해야 하며, 단순히 다음 지급이 없다고 ‘완료’로 단정하면 안 된다.

현재 소스는 지급일까지 남은 일수가 3 이하이면 연체를 포함해 빨간 왼쪽 띠, 빨간 일정 글자, 빨간 배지로 강조한다. 이번 7건 화면에서는 이 긴급 상태를 실측하지 못했다. 향후에는 실제 연체와 임박 일정을 구별하고, 일정 셀의 한 표시를 중심으로 강조하는 것이 좋다.

또한 그룹의 ‘합계’는 매매 가격과 임대 보증금 등을 더한다. 현재 잔금 완료 그룹의 24억 5,000만은 월세 보증금 3,000만과 매매가 24억 2,000만의 합이다. 서로 다른 거래유형이 섞인 전체 보기에서는 이 숫자의 업무 의미가 불분명하다. 거래유형별 합계로 명시하거나, 전체 보기에서는 건수만 표시하는 방안을 권한다.

근거: [`getNextDealPaymentSummary`, `getDealAmountValue`, 표시 함수](../../apps/desktop/src/renderer/routes/_authenticated/deals/-deal-view-utils.ts).

### 5. 셀처럼 보이는 곳이 실제로는 같은 상세 열기 동작이다

실제로 첫 행의 단계 셀을 눌렀을 때 거래 상세가 열렸다. 단계 변경은 오른쪽 `…` 메뉴에 있다. Notion에서는 상태 셀이 바로 상태 선택기를 연다.

제안:

- 매물 제목에 hover 또는 키보드 포커스 때 나타나는 ‘열기’를 둔다. 별도 버튼은 접근성 이름과 Enter 동작을 제공한다.
- 단계 배지를 실제 버튼으로 만들고, 클릭하면 기존 단계 선택·확인 흐름으로 연결한다. 기존 계약서 요구 조건과 확인 다이얼로그를 유지한다.
- `…`는 종료·취소 등 추가 관리 작업의 위치로 남긴다.
- 읽기 전용 셀에는 편집 가능한 것처럼 보이는 hover 처리를 추가하지 않는다.
- 현재 행은 `div onClick`이며 `tabIndex`와 키보드 핸들러가 없다. 제품의 기존 행 클릭 규칙은 유지하되 명시적 제목 버튼으로 키보드 접근을 보완한다.
